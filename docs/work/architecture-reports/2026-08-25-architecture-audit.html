1Extract a SlotOccupant seam from useSlotMutations.js

Evidence. src/screens/schedule/useSlotMutations.js is 1833 lines (its test is 2697). It is now the single largest non-test module in src/, larger than any screen. A slot can be occupied by one of three mutually-exclusive things — an activity, an elective set, or an event — expressed as the triple { activity_id, elective_set_id, event_id }. That triple appears 31 times across the file, and the three placement handlers are structurally near-identical:

useSlotMutations.js:628   writeSlotFields(id, { activity_id: incoming.activityId, flags: {} })
useSlotMutations.js:1650  writeSlotFields(id, { event_id: eventId, activity_id: null, elective_set_id: null, flags: {} })
        (+ the elective_set_id variant between them)

Each of the three carries its own copy of: span-tail release, optimistic route-setter projection, undo/redo closure, and displacement bookkeeping. A change to span/undo semantics must be made three times and kept in lockstep by hand — the same class of hazard the registry parity tests exist to prevent, but here with no guard.

Deletion test. The file passes it — deleting it scatters real complexity across ScheduleScreen. It earns its keep. But it fails the internal-seam test: the interesting logic (what a slot occupant is, how it displaces, how it releases a span) cannot be reached by a test without going through the whole hook. The 2697-line test file is the symptom.

Deepening move. Introduce a pure slotOccupant module — a small value-object layer that answers occupantFields(kind, id) → the write-patch, clearFields(), describe(occupant) for undo labels, and occupantOf(slot). The three placement handlers collapse to one that varies only by the occupant it is handed. The polymorphism moves behind one small, independently-testable interface; the hook shrinks and the 31 hand-maintained triples become one.

2Consolidate ImportScreen ↔ ingest duplication

Evidence. src/screens/ImportScreen.jsx is 1764 lines — now the largest screen (past ScheduleScreen at 1502). It correctly imports emitTwoRowSplit from src/ingest/twoRowSplit.js, but the "reuse" branch re-inlines a piece of that helper's own logic:

ImportScreen.jsx:647   if (existingActivity.recurrence_truth_status !== 'asserted')
                         writeFields('activities', id, { recurrence_truth_status: 'asserted' })
twoRowSplit.js:87      if (existingActivity.recurrence_truth_status !== 'asserted')
                         writeFields('activities', id, { recurrence_truth_status: 'asserted' })

The truth-status ratchet is a data-integrity rule (a one-way, information-destroying write on a synced column, per the block comment in electivePermissionTier.js). Having it authored in two places invites exactly the drift the ingest layer was extracted to prevent. ImportScreen carries 32 top-level functions and mixes UI, staging state, and commit-time op-log writes.

Deepening move. Push the reuse-decision's truth-status write behind the same src/ingest/ seam that already owns emitTwoRowSplit (e.g. an applySplitDecision(decision) that handles both reuse and split), so the screen calls one function and the rule lives once. Low effort, removes a real correctness-divergence risk on a synced column.

3Unify the special-things delete cascades

Evidence. The "contend-vs-override" family now has four parallel delete modules plus the generic one: deleteEvent.js, deleteElectiveSet.js, deleteSpecialDay.js, deleteWeek.js, over deleteRecord.js. Each hand-walks its own child tables (event_slots / special_day_slots / elective_set_activities) and must also scrub the occupant id off any template_slots referencing it.

Assessment — partial candidate, not an urgent one. The cascades have genuinely different shapes (an event owns a whole sub-schedule; an elective set owns a member list and is referenced from slots; a special day owns its own time-block/slot grid), so this is real variation across the seam, not shallow duplication — the "two adapters = real seam" test is satisfied. The risk is the shared obligation each one re-implements: when this parent dies, null its id out of every referencing template_slot, and record the op. That obligation is what should become one small deep helper the four cascades call, rather than four hand-written copies. Do not collapse the four into one god-function.

4The overloaded truth-status column (watch, don't fix yet)

activities.recurrence_truth_status was flagged in the brief as "writer but no reader." That is now outdated — it has readers: twoRowSplit.js:87 gates on it, electivePermissionTier.js and electivePermissionClear.js write/clear it, and ElectiveSetDetail.jsx reads it. The real architectural note is different and documented in the code itself: a single column is being asked to hold truths the model says coexist per occurrence-pattern (electivePermissionTier.js:10-20: "the schema's single recurrence_truth_status column can't yet hold both"). The current writers all defensively refuse to overwrite an existing asserted/obligation truth to avoid a one-way ratchet on a synced column.

This is a data-model decision, not a refactor. It is intentional data-shape-forward work with a known successor (the two-rows-sharing-a-name split). Flagging for the record; it needs an ADR and owner input, not a Maker pass. High effort, deferred.

5Registry & parity family — affirmed healthy

The audit brief asked specifically whether the accreted parallel registries have drifted or lack guards. They have not, and they do not. Deterministic findings:

  • PROJECTIONS (electron/ops/projections.js) — 30 entities including all four event tables; guarded by projectionsEntityParity.test.js, projectionsCoverage.test.js, plus per-family event.projections.test.js / electives.projections.test.js / specialDays.projections.test.js / dayOverrides.projections.test.js.
  • DOMAIN_SNAPSHOT_ORDER (campScopedEntities.js) — lists all event sub-tables with FK-ordering comments; syncClient.js:104 runs assertColumnCoverage() at import time so a table added to the order but missing from DOMAIN_TABLE_COLUMNS throws on module load. assertDirectEntityParity() guards the send/receive halves.
  • MOCK_WRITE_ALLOWLIST, UNIQUE_FIRST_FIELD, permission-matrix ENTITIES — each has a dedicated parity test (ipcSurfaceParity, uniqueFirstFieldRegistryParity, permissionsEntityParity, plus *Registries.test.js for locations/electives/specialDays/campMaps).
  • declined_two_row_splits — correctly excluded from the sync manifest: it is host-local by design (declinedSplits.js:1-3, "never synced", direct transactional SQL with no appendOp, mirroring confirmAlias.js). Registered in permissions.js and main.js as expected. No drift.

Only gap: the new event sub-tables lean on the generic parity tests rather than any test that asserts the whole event family (parent + 3 children) is registered together everywhere. Low-cost hardening: one family-completeness test, analogous to the existing per-family projection tests. Not urgent.
