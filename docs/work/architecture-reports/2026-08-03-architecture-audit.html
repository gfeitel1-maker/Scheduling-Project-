Scope and method

This audit reads the following modules in full and applies codebase-design vocabulary (depth, seam, leverage, locality, adapter) to assess each one:

  • src/screens/ScheduleScreen.jsx (1,448 lines) — known god component
  • src/screens/schedule/ — extracted hooks: useRouteState, useGeneration, useSnapshots, useSlotMutations, plus supporting pure modules
  • src/data/scheduleRepository.js — renderer-side persistence adapter
  • electron/ops/ — operations.js, projections.js, deleteRecord.js, duplicateWeek.js, deleteWeek.js
  • electron/sync/syncClient.js, syncServer.js — LAN sync layer
  • src/components/schedule/ — schedule UI components
  • src/engine/ — buildSchedule.js, weekCatalog.js, readiness.js (depth benchmark)

Methodology: apply the deletion test to every candidate — if deleting the module moves complexity to callers, it was earning its keep; if complexity vanishes or redistributes into fewer seams, the module is a shallow pass-through or misplaced responsibility. Flag god components, shallow pass-throughs, seam misplacement, missing internal seams, and premature seams. Report only what is confirmed from reading the actual files; no speculative performance claims without a measured baseline.

Depth benchmark: the pure engine

Deep module reference — src/engine/buildSchedule.js

Interface: one function, one object argument, one return value. No React, no IPC, no side effects. The seam is the function signature.

Implementation depth: three-pass scheduler (eligibility resolution → high-priority placement → low-priority placement → audit), seeded PRNG, span-block logic, two call signatures, backward compatibility shim, per-session findings aggregation.

Deletion test: delete this module and ~600 lines of scheduling logic disperses across callers. Passes.

Why it matters as a benchmark: every unit of interface (one function call) purchases every unit of implementation (the entire scheduler). Locality is perfect — all schedule-build bugs live here. Every other module in the audit is scored against this standard.

Second benchmark — electron/ops/operations.js

Interface: appendOp, appendBulkReplaceOp, detectConflict, recordConflict, coerceOpValue, latestScopeOpSeq. Eight named exports.

Implementation depth: SQLite transaction management, op-log append, value coercion (boolean/object/buffer), conflict detection, bulk-replace lifecycle (validate → delete → insert → log), idempotency via client_write_id, op-log replay.

Deletion test: passes. Complexity collapses into every caller that touches the DB.

Verdict: deep. The interface is not minimal (8 exports vs. 2 for buildSchedule) but each export is a genuinely distinct primitive with real implementation depth behind it.

Deepening candidates

#1
High leverage God component Missing internal seam
Extract loadAll into useScheduleData

What the code does now

loadAll is a 150-line async function declared inside ScheduleScreen (lines 263–416). It spans four distinct sub-concerns in a single sequential body with four independent try/catch blocks:

  1. Load setup lists (groups, days, timeBlocks, activities, anchors, tiers, cohorts) and sort/filter them by campId — ~40 lines.
  2. Load, filter, and lazy-create schedule weeks; resolve liveWeekId — ~45 lines.
  3. Load week exclusions — ~10 lines.
  4. Load template data (templates, slots, overlays, snapshots), resolve template IDs for both routes, compute initial stats and findings, and bulk-set all route-scoped state — ~65 lines.

Because loadAll is a closure over 12+ state setters from the enclosing component, none of its four sub-concerns can be tested or reasoned about without mounting the full screen.

Deletion test

Delete loadAll: all four sub-concerns disperse back into callers or must be re-created inline. Delete the screen instead: none of the logic vanishes — it all lives in one place. The function is earning its keep as an aggregator, but its internal seams are invisible from the outside, making it unmockable and untestable as a unit.

Proposed seam

A useScheduleData({ campId, weekId, repo, routes }) hook with a single return shape:

{ setupLists, weeks, weekId, exclusions, templateData, loading, loadError, templateError, reload }

The hook owns all four data-fetch concerns. The screen owns only React state that is genuinely UI-level: view, railView, editSlot, generating, etc. recalcStats and ensureTemplateRow (which are also currently inline closures) migrate with the hook, since both depend on the same loaded data.

Leverage

Every test that needs to assert "the screen shows an error when week loading fails" currently needs a full React render with mocked IPC. A useScheduleData hook tests that behaviour directly — no render, no DnD context, no modal wiring. This is the highest-leverage extraction remaining in the schedule layer.

Evidence: src/screens/ScheduleScreen.jsx lines 263–416, 418–443 (effects), 445–475 (inline helpers). loadAll calls setGroups, setDays, setTimeBlocks, setActivities, setAnchors, setTiers, setCohorts, setWeeks, setWeekId, setActivityExclusions, setGroupExclusions, setExistingTemplates, setTemplateIdByRoute, setSlotsByRoute, setOverlaysByRoute, setSnapshotsByRoute, setStatsByRoute, setFindingsByRoute, setDismissedByRoute, setLoading, setLoadError, setTemplateError — 22 distinct setters. That is 22 seam crossings for one logical concern.
#2
High leverage God component Missing internal seam
Merge handleGroupDragEnd / handleDayDragEnd

What the code does now

handleGroupDragEnd (lines 496–536) and handleDayDragEnd (lines 545–597) are two 90-line functions that are structurally identical. Both handle three cases in the same order: expand-drag, palette-activity drop, slot-swap. The expand-drag and palette-drop branches are byte-for-byte the same logic; slot-swap only exists in the day-view handler. The only structural difference is that handleGroupDragStart/handleDayDragStart each set a different isExpandDragActive flag.

Evidence: Lines 496–536 vs. 545–597. Both functions contain: 
const expandDrag = active.data.current?.expandDrag
const paletteActivity = active.data.current?.paletteActivity
if (expandDrag) { ... const headBlock = timeBlocks.find(b => b.id === headBlockId) ...
  expandSlot(groupId, dayId, headBlockId, tailBlockId, ...) }
Identical in both. The two DndContext wrappers at the bottom of the render (lines 1296–1321) instantiate them separately, but the handler logic does not structurally differ by which DndContext is active — only by which isDragActive flag is set.

Deletion test

Delete handleGroupDragEnd and replace it with handleDayDragEnd: no logic disappears. The expand-drag and palette-drop paths are exactly as present. Slot-swap was only in the day handler anyway. The duplication fails the deletion test — removing one does not reduce overall complexity.

Proposed seam

A single handleDragEnd({ active, over, context }) where context = { setIsExpandDragActive, allowSwap } distinguishes the two cases. The two DndContext wrappers remain (they are the right seam for DnD scope isolation); they just pass different context values to the same handler. The two separate DragStart handlers reduce to one setter call parameterised by flag.

Leverage

A single handler is testable once. The current duplication means any bug in expand-drag or palette-drop must be fixed in two places and tested in two places. This is a locality failure — the same bug can exist in one copy but not the other with no indication.

#3
Correctness gap Seam misplacement
Unlock is_locked in the activities projection

What the code does now

electron/ops/projections.js PROJECTIONS.activities.fields (lines 128–145) explicitly excludes is_locked. The comment on line 123 explains: "is_locked is deliberately excluded — ScheduleScreen.jsx ... still writes activities.is_locked directly via Supabase". Supabase has been fully retired. @supabase/supabase-js is not a dependency, and an ESLint rule bans any new Supabase import.

The current write path

useSlotMutations.lockActivity(activityId) calls repo.writeActivityFields(activityId, { is_locked: true }), which calls writeFields('activities', activityId, { is_locked: true }), which calls localClient.write(token, 'activities', activityId, 'is_locked', true). On the Electron main process, handleSubmitOp calls appendOp. appendOp checks:

if (projection && field !== DELETE_FIELD && !projection.fields.includes(field)) {
  throw new Error('field not allowed for entity')
}

Since 'is_locked' is not in PROJECTIONS.activities.fields, this throws. The caller catches it and sets actionError. Every call to Lock Activity currently fails silently with a generic error banner.

Fix

Add 'is_locked' to PROJECTIONS.activities.fields and remove the stale comment. Confirm that normalizeSlots does not need a matching read-side decoder (it does not — is_locked is a simple integer column, read back as-is by better-sqlite3).

Why this is an architecture finding, not just a bug

The write path for is_locked crosses the correct seams (IPC → op-log → projection). The gap is that the projection registry acts as a field-level allowlist that was never updated when the write path migrated. The allowlist is an architectural invariant of the op-log design — any field omitted from it silently fails. This is a seam that the architecture depends on but which is not visibly tested at the seam boundary (the 'field not allowed for entity' throw is tested in operations.test.js but not for this specific field).

Evidence: electron/ops/projections.js lines 122–126 (comment + field list). src/screens/schedule/useSlotMutations.js lines 187–196 (lockActivity). src/data/scheduleRepository.js line 188 (writeActivityFields). electron/ops/operations.js lines 77–80 (the throw).
#4
Medium leverage Shallow IPC seam
Add scope-filtered reads to the IPC layer and repository

What the code does now

scheduleRepository.reloadSlots(templateId) calls localClient.list('template_slots') — which returns every template_slots row for the camp — and then filters in the renderer:

async reloadSlots(templateId) {
  return normalizeSlots(await localClient.list('template_slots')).filter(s => s.template_id === templateId)
}

Same pattern in reloadOverlays, getSnapshot, loadWeekExclusions, and the template-data aggregation in loadTemplateData. The IPC layer exposes list(entity) with no predicate. All filtering is caller-side in the renderer.

Why this matters architecturally

The seam between the renderer and the main process is IPC. Any concern that should be resolved before crossing the seam (e.g., "which template's slots?") that is instead resolved after crossing it — in the renderer — is seam misplacement. As the number of weeks per camp grows (multi-week was just shipped), the volume of rows per list call grows proportionally. reloadSlots is called after every slot mutation: every drag-and-drop now loads all slots for all routes and all weeks, discards the irrelevant ones, and normalises the survivors.

Proposed seam

Add a listByScope(entity, scopeColumn, scopeId) primitive to the IPC bridge (window.shoresh.listByScope), backed by a parameterised SELECT ... WHERE scopeColumn = ? in electron/main.js. The repository then calls:

async reloadSlots(templateId) {
  return normalizeSlots(await localClient.listByScope('template_slots', 'template_id', templateId))
}

The filtering moves to SQLite — where it belongs — and the renderer receives only the rows it will use.

Deletion test

The current pass-through is not entirely shallow: normalizeSlots is real depth. But the list → filter pattern itself is a pass-through that adds interface cost (callers must know about template_id as a filter key) while doing no work inside the seam.

Evidence: src/data/scheduleRepository.js lines 106–108 (reloadSlots), 110–112 (reloadOverlays), 114–115 (getSnapshot), 91–103 (loadTemplateData aggregation).
#5
Medium leverage Shallow module
Deepen useRouteState with a bulk-update method

What the code does now

useRouteState is 90 lines. Its interface exports 16 values. The implementation holds 8 useState atoms, derives 6 current-route accessors, wraps 6 current-route setters, and exports the 8 raw setters as well. The interface-to-implementation ratio is near 1:1 — nearly every state atom appears directly in the return value.

The one genuine depth contribution is routeSetter — a helper that turns a by-route setter into a route-scoped setter, shared with useGeneration and useSnapshots. This is earning leverage: 3 callers use the same adapter without re-implementing it.

Deletion test

Delete useRouteState: its callers would hoist 8 useState calls and inline routeSetter. The deletion test is ambiguous — some complexity disperses, but the pattern is widely used enough that the centralisation has real locality value. This is a shallow-ish module rather than a pure pass-through.

Proposed deepening

Add a bulk-update method setRouteData(route, { slots, stats, findings, dismissed, overlays, snapshots }) that sets all six route-scoped atoms atomically in a single render. Currently, loadAll calls 6 separate set*ByRoute calls for each route in a loop — 12 potential re-renders batched only by React 18's automatic batching. A single setRouteData call is explicit, readable, and cannot partially-update a route's state.

The hook's interface narrows: callers who perform bulk loads (just loadAll) use setRouteData; callers who update one field use the existing current-route setters. The by-route raw setters (setSlotsByRoute, etc.) can be hidden as internal — they are only used by loadAll and the bulk-init in EMPTY_BY_ROUTE, not by the mutation hooks.

Evidence: src/screens/schedule/useRouteState.js entire file (90 lines, 16 return values). src/screens/ScheduleScreen.jsx lines 363–411 (6 separate set*ByRoute calls inside loadAll's loop over ROUTES).
#6
Low leverage (document and contain) Op-log invariant deviation
The raw-SQL pre-insert in duplicateWeek.js

What the code does now

duplicateWeek.js line 72–74 executes a direct INSERT OR IGNORE INTO schedule_weeks inside the transaction, before any ops are appended:

db.prepare(
  "INSERT OR IGNORE INTO schedule_weeks (id, camp_id, name, sort_order, is_archived) VALUES (?, ?, '', 0, 0)"
).run(newWeekId, camp?.id ?? campId)

This violates the op-log-only write invariant: all mutations to synced entities go through appendOp, never a direct bypass (CLAUDE.md). The comment explains the reason — child rows (schedule_templates.week_id) carry a NOT NULL FK to the week, so the week row must exist inside the same transaction before the template ops fire.

Why it is not a critical failure

The raw insert creates a placeholder row (name = '', sort_order = 0). The ops appended at the end of the same transaction then UPDATE that row with correct values via applyProjection. On the creating device, the final row state is correct. On a peer, the ops replay through the op-log via applyRemoteOp, where schedule_weeks.ensureExists handles the INSERT via its own INSERT OR IGNORE. So the state converges correctly across devices — the raw insert is local-only scaffolding, not data that bypasses replication.

Remaining concern

The raw insert is not auditable — it does not appear in the operations log, so the week's initial creation event has no log entry. An observer inspecting the op-log to understand a camp's week history will see the name write as the first event, not the row creation. More practically: if the transaction is rolled back after the raw insert (e.g., a duplicate client_write_id or a constraint violation in the ops), the raw insert is also rolled back — so no partial state leaks. The concern is documentation and auditability, not correctness.

Recommendation

Add a comment at lines 69–74 that explicitly names this as a deliberate invariant deviation and explains why it is safe (FK constraint, same transaction, UPDATE follows immediately). The existing comment is partial; a future maintainer reading "break the genuine cycle" should not have to reconstruct the safety argument. No code change required unless the op-log needs to be made auditability-complete for this event.

Evidence: electron/ops/duplicateWeek.js lines 68–74. The raw insert is inside db.transaction() at line 61. Ops are appended in lines 64–201. The week row ops are appended last (lines 178–201) per the §3.4 ordering requirement.

What is clean

The following areas passed the deletion test or showed genuine depth and are not flagged for deepening work:

  • useSlotMutations — 507 lines, 11 handlers, each with a repo write + undo closure. Correctly owns no state. The hoisted addOverlay/updateOverlayRange wrappers that break the cycle with useOverlayFillStamp are a deliberate and documented seam choice, not a misplacement.
  • useSnapshots — 4 CRUD operations over the repository; no state owned; route-explicit saveSnapshot(routeName) correctly uses the explicit setter rather than the current-route one.
  • useGeneration — explicit-route setters in both generate and placeAnchors (not current-route) correctly handle first-run invocation before the route switch is committed to React state.
  • scheduleRepository — the single mapSlotToRow mapper with { spanHead } discriminator is the right shape for two divergent call paths. The writeFields private helper correctly surfaces the first failure rather than silently partial-writing. The injection pattern (localClient, getToken) makes the seam the test surface.
  • deleteRecord.js — the count-contract (preview and execute use the same query), snapshot-first order, and per-entity delete strategy are all locally correct and well-documented.
  • deleteWeek.js — cascade order is explicit and matches FK topology. Conflict closure step 6 is correct.
  • Sync layer (syncClient/syncServer) — the seam between renderer and sync is IPC, not imported modules. Renderer has no sync topology knowledge. The DOMAIN_SNAPSHOT_TABLES ordering in syncClient is FK-correct for the tables it lists.
  • Component layer — SlotCell, ScheduleGroupView, ScheduleDayView, etc. accept computed geometry via the injected geometry object and do not reach back into screen state. They are wide (many props) but earn the width — each prop corresponds to a genuinely distinct presentational concern.
  • gridGeometry.js, findingHighlight.js, slotCellConstants.js — pure functions with no React or IPC. Deep by the engine standard.
