Sync + Auth Architecture Audit

Shoresh · 2026-08-16 · F4 follow-up from the 2026-08-16 audit · read-only, HEAD b693e98 · scope: electron/sync/* + electron/auth/*

This is the dedicated deep-read pass F4 called for: syncClient.js (1,489 lines) and syncServer.js (1,227 lines) had only been partially read in prior audits. The verdict up front: the layer is structurally healthier than its line count suggests. The domain logic lives elsewhere (electron/ops/*), the renderer is fully insulated behind IPC (it never imports a sync module and only ever sees a write/isConnected/onConnectionChange surface), and the auth core is a clean single seam. The genuine debt is two un-extracted internal seams inside the two big files, plus a device-trust check duplicated across four call sites.

Active-work caveat. Branch claude/t87-returning-client-reauth is concurrently reworking returning-client reauth. Candidates C1, C3, and C4 below touch the reauth / re-authenticate / device-trust path and are tagged MAY OVERLAP T87 — verify against that branch before acting. The structural findings themselves (module depth, seam placement) are largely orthogonal to T87's logic fix, but the exact lines overlap.

The auth ↔ sync token seam is coherent

Before the candidates, the one boundary the brief flagged as possibly "tangled": how camp vs. local tokens, signing keys, and device trust flow across the three files. It is not tangled. The rules are single-sourced and each side owns exactly what it should:

  • Minting authority is derived, never asserted. issueTokenForThisDevice (localAuth.js:193) picks camp vs. local token purely from the presence of host_signing_key on this device — a caller cannot mint the wrong kind.
  • The network rejects local tokens explicitly. handleAuthenticate closes with code 4402 on any non-camp token (syncServer.js:396) rather than relying on signature mismatch — a local token from the same device would otherwise verify.
  • Write-action derivation is single-sourced. Both the IPC path (main.js) and the WS path (handleSubmitOp/handleAcquireLock) call the same deriveWriteAction, so staff cannot do over WS what they cannot do over IPC.
  • Provenance is host-derived on the trust boundary. handleSubmitOp forces source:'human' and never copies msg.op.source (syncServer.js:649).

This part of the layer is a positive example. The candidates below are about size and internal seams, not this boundary.

Ranked deepening candidates

C1 Extract the reliable-delivery + catch-up watermark sub-module out of syncServer.js High
missing internal seam multi-responsibility file MAY OVERLAP T87

Roughly 330 lines of syncServer.js form one cohesive concern that has nothing to do with message routing: guaranteeing an op is genuinely delivered-and-applied before a device's watermark advances. It spans send, sendWithAck, waitForFullSyncAck, waitForApplyAck, currentMaxOpSeq, sendFullSyncIfFirstPairing, and sendMissedOps (syncServer.js:40–374). It carries its own hard invariant — the watermark advances only to the seq of the last op whose apply-ack genuinely returned, in order, with no gaps — a property that has already been re-derived across three rounds of fixes (Task 10 rounds 4/5/6, then T85 Part 2).

Deletion test: deleting this cluster would move a genuinely separate, invariant-bearing concern onto the message router's callers — it does not simplify. That is the signature of a real seam waiting to be named.
Already straining to be a module: sendMissedOps and sendWithAck are already exported solely for direct unit testing (comments at :290 and :71). The test cannot reach the watermark logic except through the whole server today; a opDelivery.js / catchup.js module would give it a first-class seam.

The T87 overlap: the clobber hazard these ack-waiters create — each stashes a single resolver on the socket (ws.pendingFullSyncAckResolve, ws.pendingCatchupAckResolve/OpId) — is exactly what forced the isReauthenticate early-return guard (:464–480), and that reauth path is what T87 is reworking. Fold the fix (C4) in when extracting.

C2 Single-source the full_sync snapshot manifest shared by server and client High
seam misplacement duplicated cross-file knowledge

The set of camp-scoped tables shipped in the first-pairing snapshot, and their FK-safe apply order, is knowledge that must agree between the two ends of one wire — yet it is written twice, in two shapes, in two files. The server enumerates it as DIRECT_CAMP_ENTITIES + DOMAIN_PARENT_SCOPED_ENTITIES and ships SELECT * (syncServer.js:33, 184–195); the client re-lists the identical tables plus an explicit per-column allowlist and ordering as DOMAIN_SNAPSHOT_TABLES + DOMAIN_TABLE_COLUMNS (syncClient.js:34–76).

The divergence is not hypothetical — it already exists. The server-side comment at syncServer.js:26–32 states plainly that week_location_exclusions (and its two week_*_exclusions siblings) are in the server's snapshot list but not in the client's DOMAIN_SNAPSHOT_TABLES, so "a first-pairing Client currently drops these rows." Two hand-maintained lists that must match have already drifted. A shared snapshotManifest.js (tables, order, columns, validators) consumed by both ends makes the drift impossible by construction and is the natural home for closing that gap.

Leverage is high because the two lists will keep drifting every time a camp-scoped table is added (the pattern has recurred at v28, v32, v33), and each drift silently drops rows on exactly the devices — brand-new Clients — least able to notice.

C3 Collapse the device-trust gate into one predicate Medium
shallow duplication seam misplacement MAY OVERLAP T87

The rule "is this device currently allowed to act" — authorized_at set, revoked_at null — is re-queried and re-checked by hand in at least four places: authorize() (authorize.js:43–62), handleAuthenticate (syncServer.js:418–444), handleLogin (syncServer.js:521–525), and the renew_token branch (syncServer.js:1136–1142). Each re-implements the same SELECT and the same two-branch check, differing only in the close code / reply shape it emits (4403/4404/login_failed/token_renewal_failed).

Deletion test: a single deviceTrustStatus(db, deviceId) → 'ok' | 'not_authorized' | 'revoked' | 'unknown' predicate would let each call site keep its own response mapping while removing four copies of the query-and-branch logic. The duplication is shallow (each copy is nearly its whole value), and a new device-state (e.g. the 'unknown' stub row T85 introduced, syncClient.js:492) currently has to be reasoned about at every copy independently.

T87 overlap: returning-client reauth exercises exactly these authenticate/authorize device checks; land after T87 or coordinate.

C4 Replace the ws-stashed single ack-resolvers with a keyed pending-ack registry Medium
missing internal seam MAY OVERLAP T87

On the server, each in-flight ack is a bare property on the socket object: ws.pendingFullSyncAckResolve, ws.pendingCatchupAckResolve + ws.pendingCatchupAckOpId (syncServer.js:134–153, 272–288). Because there is only one slot per kind, a second concurrent run clobbers the first — which is precisely the failure the isReauthenticate guard exists to dodge (:446–480), and the reason its long comment has to argue that a second catch-up is "both unnecessary and the sole source of the clobber."

The good pattern already exists on the other side. syncClient.js solved the identical problem with restoreResolvers/deleteResolvers/mergeResolvers keyed by request_id, plus a single keyedResolverMaps registry drained uniformly on disconnect (syncClient.js:323–331, 815–820). Mirroring that on the server — a per-connection map keyed by op_id / sync-phase — removes the clobber hazard structurally, which in turn removes the reason for the guard rather than papering over it.

This is the mechanism-level companion to C1; extract them together. Heavily entangled with the T87 reauth rework — coordinate directly.

C5 Name the two identities of createSyncClient Low
split identity behind one factory

createSyncClient returns two structurally different objects depending on whether serverUrl is set. The no-serverUrl (Host-local) branch (syncClient.js:179–279) is ~100 lines implementing its own write/writeBulkReplace that append directly and broadcast via wss, alongside a set of inert stubs (isConnected → false, flushQueue → {}). It shares almost no runtime path with the remote client below it; it is effectively a second class sharing a constructor and an interface.

This is a mild observation, not a defect: the shared interface is the point, and the stubs are honestly documented. But the two halves never interact, so a reader must hold "which client am I in" in their head for 1,300 lines. A named createHostLocalClient vs. createRemoteClient split (behind the same factory dispatch) would let each be read and tested in isolation. Low leverage; list it, don't prioritize it.

Benchmarks — what "deep" looks like in this layer

authorize.js — the canonical deep auth module

A 94-line file with one exported function and a narrow signature ({db, token, action, resourceId}) hiding a deep guarantee: every privileged action re-derives role and device trust from the database, never from the token payload, so a revoked device or demoted user is denied on its very next call. The resourceId parameter is accepted-but-unused specifically so a future per-resource rule needs no signature change — a deliberate, documented forward seam, not a premature one.

discovery.js — minimal, boundary-correct

39 lines. toValidatedHost treats every mDNS broadcast as untrusted input and returns null on any shape mismatch. No abstraction it doesn't need; no adapter for a variation that doesn't exist.

What was checked and found clean

  • Renderer sync-topology leakage: none. The renderer never imports syncClient/syncServer; it reaches the data layer only through window.shoresh.* IPC. The only topology it sees is isConnected() / onConnectionChange() — "can I reach the host," deliberately the minimum, explicitly documented as read-only (syncClient.js:1216–1219).
  • Op-log internals leaking to clients: the wire vocabulary (op_applied, op_conflict, op_rejected, watermarks) is the sync protocol itself, not a leak of storage internals; row shape is re-validated on receipt (isValidRemoteOp).
  • Premature seams: none found. Every seam crossed (IPC, ops/*, lockManager, rateLimit) has real variation behind it.
  • localAuth token seam: camp/local dispatch is derived, not asserted; verification fails closed on every malformed path.

End of report. Candidates ranked by leverage: C1 & C2 high, C3 & C4 medium, C5 low. C1/C3/C4 touch the T87 reauth surface — verify against claude/t87-returning-client-reauth before acting.
