Scope and method

This audit reads the schedule screen, its extracted hooks, the renderer data adapter, the op-log primitives/projections/week mutations, and the schedule component and engine layers, applying codebase-design vocabulary (depth, seam, leverage, locality, deletion test). It is read-only; it produces deepening candidates, not code.

Methodology: apply the deletion test to every candidate. If deleting the module moves complexity to callers, it earned its keep; if complexity vanishes or redistributes into fewer seams, the module is a shallow pass-through or misplaced responsibility. Flag god components, shallow pass-throughs, seam misplacement, missing internal seams, locality failures, and premature seams. Report only what is confirmed from reading the actual files.

#1
High leverage Locality failure Missing internal seam
Extract the optimistic-write + undo/redo envelope in useSlotMutations

What the code does now

useSlotMutations.js has grown from 507 to 844 lines. The growth is the per-cell write-serialization queue (cellQueueRef + claimAndRun, lines 120–171) added for the live write-ordering race (memory: PR #54). The queue itself is a genuine deep primitive. The problem is how it is consumed: four mutation handlers — replaceSlot (219–308), placeActivityManual (490–548), expandSlot (588–666), and splitSlot (697–782) — each hand-repeat the same five-step envelope:

const outcome = await claimAndRun(keys, claimId, async () => { /* repo writes */ })
if (outcome.dropped) return                 // superseded before dispatch
setSlots(prev => prev.map(/* optimistic patch */))
pushUndo({
  undo: async () => { const o = await claimAndRun(keys, crypto.randomUUID(), ...); if (o.dropped) return; setSlots(...) },
  redo: async () => { const o = await claimAndRun(keys, crypto.randomUUID(), ...); if (o.dropped) return; setSlots(...) },
})

The invariant this envelope encodes — every write, including undo and redo, must go through claimAndRun with a fresh claim id, and must no-op silently when dropped — is not expressed once. It is re-typed in each handler and again inside each handler's undo and redo closures. That is roughly a dozen open-coded copies of the same queue-participation contract.

Deletion test

There is no seam to delete — the contract has no name. A reader who wants to know "does undo also respect the write queue?" must read all four handlers and confirm each closure independently. Memory records this exact failure mode already occurred: the first queue implementation "missed placeActivityManual", reopening the race. A hand-repeated invariant with a history of being missed in one copy is the definition of a locality failure.

Proposed seam

A single higher-order helper inside the hook — runMutation({ keys, apply, invert, describe }) — that owns the claim/dispatch, the dropped-return, the optimistic setSlots, and the construction of the pushUndo({ undo, redo }) pair (each branch re-entering runMutation with a fresh claim). Each handler then declares only what changes (the forward patch and its inverse), never how the queue and undo stack are wired. The queue-participation contract lives in exactly one place and is tested once.

Leverage

Highest remaining in the schedule layer. It removes ~4× duplication of the most safety-critical invariant in the mutation path (the one that guards UI/DB convergence under concurrent drags), and it makes the contract testable at a single seam rather than by asserting queue behavior separately for every handler.

Evidence: src/screens/schedule/useSlotMutations.js — envelope repeated at lines 219–308, 490–548, 588–666, 697–782; each with matching claimAndRun-wrapped undo/redo at (263/286), (521/536), (624/645), (734/755). Queue primitive at 120–171. Memory note "DnD FSM / write serialization": queue v2 originally missed placeActivityManual.
#2
Medium-high leverage Locality failure Divergence risk
Lift the duplicated eligibility predicate to one shared rule

What the code does now

"Which activities may a group do" is computed by the same tier/group-id rule in two places:

  • ScheduleScreen.jsx:220–231 — eligibleActivitiesFor(groupId), passed down to ManualBuildView, ScheduleGroupView, and ScheduleDayView for the inline typeahead.
  • useSlotMutations.js:414–417 — the identical predicate inside placeActivityManual, deciding whether a placed slot earns an UNFILLABLE flag.

The comment at ScheduleScreen.jsx:215–216 asserts the rule was "lifted so both the drag path and the typeahead read one definition." It was not lifted into a shared module — the hook keeps its own copy. The comment describes an intent the code does not honor, which is worse than silence: a future maintainer trusts a single source of truth that does not exist.

Deletion test

Delete either copy and the other does not cover it — the typeahead and the flag logic would silently disagree about eligibility. The two copies pass the "earns its keep" test individually but fail locality: the same rule, two homes, one misleading comment claiming otherwise.

Proposed seam

A pure predicate — isActivityEligible(activity, group) (and a thin eligibleActivitiesFor(activities, group) over it) — in a React-free module alongside the engine's own eligibility notion. Both the screen and the hook import it; the misleading comment is deleted because it becomes true. Bonus: this is the same concept buildSchedule resolves in its eligibility pass, so the shared predicate is a candidate to align the manual-route flag logic with the engine's own rule rather than a parallel restatement of it.

Leverage

Medium-high. Small extraction, but it removes a correctness-divergence seam on a rule that decides both what the director is offered and whether a placement is flagged — the two must never disagree.

Evidence: src/screens/ScheduleScreen.jsx lines 215–231 (predicate + false "one definition" comment). src/screens/schedule/useSlotMutations.js lines 414–417 (second copy). Consumers: ManualBuildView.jsx:177, ScheduleGroupView.jsx:235, ScheduleDayView.jsx:202.

Extract findings-rail derivation out of ScheduleScreen

What the code does now

After the C1/C2/C5 extractions the screen is 1,281 lines with 19 useState calls. Data-fetch, route state, mutations, snapshots, weeks, and generation are all out. What remains largest and least UI-shaped is the findings-rail derivation: roughly ScheduleScreen.jsx:448–559 computes unfillableSlots, overlapSlots, activeFindings, then builds and sorts findingsRows (with per-route copy in findingReason/slotLocator), and derives highlightMap, highlightedKind, railRows, and the off-view visible-count. This is ~110 lines of pure, route-aware transformation from (slots, findings, dismissed, view, selection) to (rows, highlight map, counts) — no JSX, no state ownership, threaded through the render only.

Deletion test

This block is a pure function trapped inside a component. To test "the rail shows 3 of 8 lit here" or "manual route rewrites UNDERSERVED copy" you must mount the whole screen with DnD context and mocked IPC. Delete the screen and the logic does not vanish — it is self-contained; it simply has no seam of its own.

Proposed seam

A pure module deriveFindingsRows({ slots, findings, dismissed, route, groups, activities, days, timeBlocks }) returning { rows, highlightMap, highlightedKind, highlightColor, railRows, counts }, mirroring how gridGeometry.js and findingHighlight.js already sit beside the screen as pure helpers. The screen keeps only railView (UI toggle state) and renders the returned rows. This is the same move that made C1 pay off, applied to the last large inline concern.

Leverage

Medium. Lower than F1/F2 because the block is correct and already fairly localized; the payoff is testability of the route-divergent findings vocabulary (UNFILLABLE vs OVERLAP, manual copy rewrites) without a render, and shrinking the god component's last big non-JSX region.

Evidence: src/screens/ScheduleScreen.jsx lines 448–559 (findingsRows build at 489–516; highlightMap/highlightedKind at 522–545; off-view count at 538–545). Precedent pure helpers: src/screens/schedule/gridGeometry.js, findingHighlight.js.
