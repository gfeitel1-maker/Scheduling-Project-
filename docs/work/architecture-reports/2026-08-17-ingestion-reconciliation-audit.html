Ingestion + Reconciliation Architecture Audit

Shoresh · 2026-08-17 · read-only, HEAD d412fdb · scope: electron/ops/ingest.js + src/ingest/* + src/screens/{ImportScreen,ReconciliationScreen,ReadinessHub} and their models

This is the first architecture pass over the ingestion/reconciliation subsystem — the largest recently-built area of the app, untouched by the 2026-08-03 (schedule) and 2026-08-16 (sync/auth) audits. The verdict up front: this subsystem is structurally healthy, and healthier than its accretion history would predict. It was built slice-by-slice across a dozen ADRs (S0 → S1a → S2a/b/c → S4b → T72/T73 → M4 → Phase C), and that history shows as accumulated commentary, but the seams landed in the right places. The pure decision/projection layer (buildPlan, buildReconciliationReport, reportToLanes, and the renderer triage models) is exemplary — pure, small-interfaced, exhaustively tested, and directly comparable to buildSchedule.js. The renderer never touches SQL and only ever crosses the IPC seam. The genuine debt is concentrated: one very large write function (commitPlan) with several un-extracted internal seams, and one god component (ImportScreen.jsx) whose parse-stage orchestration never got the model-extraction its reconciliation-stage sibling did.

Active-work caveat. A concurrent initiative (worktree claude/shoresh-ingestion-reconciliation-ad07ae) is actively redesigning the reconciliation UI, governed by docs/adr/2026-08-17-onescreen-reconciliation-projection.md (landed today). Candidates that touch the import/reconciliation screen surface are tagged MAY OVERLAP ACTIVE INITIATIVE — verify before acting. The structural findings on the write path (commitPlan) are largely orthogonal to that UI redesign and are the more durable targets.

The dry-run-as-preview seam is a positive example

Before the candidates, the boundary the brief asked about most directly — how observations/inferences/confirmations flow from ingest to the director's decisions — is coherent and worth protecting. The preview is not a parallel re-implementation of the commit; it is the commit, run with dryRun:true. ingestReconcile calls the same commitIngest → commitPlan transaction, computes the real plan / provenance / evidence, then rolls the transaction back and returns those artifacts (ingest.js:541–547). The renderer feeds them to the pure buildReconciliationReport, projects to lanes, and folds the director's triage answers back into the same payload shape the commit accepts (reconciliationTriage.foldTriageInputs). One decision engine, exercised twice. This is depth-positive: preview and commit cannot disagree by construction, and no SQL or IPC detail leaks into the renderer. No seam-misplacement finding exists here — that is a deliberately good result to record.

Ranked deepening candidates

C1 Extract the fixed-event ingest (recognize / create / move-drift / scope-drift) out of commitPlan High
missing internal seam multi-responsibility function

Inside the ~650-line commitPlan, roughly ingest.js:1247–1461 is one cohesive sub-algorithm with nothing to do with the generic per-entity create/update writer around it: anchor-slot recognition, the read-only set-cardinality move-drift pre-pass (liveByGroup/fileByGroup/movedBySlot), scope-drift detection, and the fixed-event write loop. It carries its own hard invariants (slot identity excludes scope; move-pairing is 1:1 per (cohort, name) group; the pre-pass appends no ops) that have already been re-derived across T72, C1a, C1b, and C3.

Deletion test: lifting this cluster into an anchorReconcile.js that takes the seeded name maps + live-anchor scan and returns { toWriteAnchors, moved, scopeChanged, ... } does not push complexity onto callers — commitPlan is the sole caller and shrinks by a third. That is a real seam waiting to be named, not a pass-through.
The test cannot reach it today: the move-cardinality logic is the most subtle code in the file, yet it is exercisable only by driving a whole workbook through commitIngest. A pure module would give the drift analysis a first-class, directly-testable surface — the same win buildSchedule.js gets from being pure.

Highest-leverage of the write-path findings, and largely stable against the UI redesign (the fixed-event report shape is already an established contract consumed by buildReconciliationReport).

C2 Extract an import-session model out of ImportScreen.jsx (the parse stage never got what the reconciliation stage did) High MAY OVERLAP ACTIVE INITIATIVE
god component logic trapped in component

ImportScreen.jsx (1,263 lines) holds ~26 useState atoms and at least four distinct responsibilities: (1) file reading + the parse/infer pipeline orchestration (readFiles, ingest.js:171–319, chaining XLSX.read → extractEntities → buildPreview → inferFixedEvents → inferActivityRules); (2) rule/fixed-event/unit editing (updateActivityRule, toggleRuleGroup, groupUnitOverrides…); (3) commit-input assembly (buildCommitInputs, :445–537); and (4) the full ~600-line render plus two nested sub-components. The pure pieces it calls are well-extracted; the orchestration and session state that wires them are not.

The asymmetry is the tell: the reconciliation half of the same flow was decomposed into reconciliationTriage.js, reconciliationResolutions.js, and importOutcomeModel.js — pure, React-free, directly tested. The parse half has no equivalent useImportSession / importPlan.js seam, so its multi-step state machine (which file, which preview, which chosen entities, which mode) is testable only by mounting the whole screen. This is exactly the decomposition ScheduleScreen received (useRouteState et al.).
Deletion test: the extracted model earns its keep across the screen's many handlers and its re-import path (handleWorkbookReimport), and would make the parse-stage state independently testable — complexity concentrates, it does not spread.

Tagged as overlapping because the active one-screen initiative is reworking this surface; the model extraction may be subsumed, superseded, or best done as part of that initiative rather than against it. Confirm scope with that branch before starting.

C3 Name the per-item decision closures inside commitPlan as a testable decide-phase Medium
missing internal seam multi-responsibility function

Beyond the fixed-event block (C1), commitPlan defines ~10 further closures over shared mutable state — decideFieldItem, makeConflict/makeStaleConflict/makeFieldConflict/makeMissingTarget, commitCreate, commitUpdate, seedRecognitionMaps, resolveOrCreateLocationId — each closing over conflicts[], created{}, and the name maps. The Policy-A protection gate and the base-generation staleness clock (the subsystem's most security-relevant logic, deciding what a re-import may silently overwrite) live inside decideFieldItem (:1090–1150) and can only be tested through a full commit.

Depth is fine; navigability and test-reach are the cost. The external interface is genuinely small and the module is heavily tested (30+ ingest test files) — this is a deep module, not a shallow one. But the decide phase (walk plan → classify each item into toCreate/toUpdate/conflicts, no writes) is already conceptually separated from the write phase; making that split structural — a pure decide(plan, recognition, live) returning the three lists — would let the gate logic be unit-tested directly without a DB transaction.

Lower leverage than C1 because it is refactor-for-testability of already-correct, already-tested code rather than closing a gap; sequence it after C1, with which it shares the file.

C4 Single-source the recognition/scoping rule shared by buildExistingSnapshot and seedRecognitionMaps Medium
duplicated cross-layer knowledge seam kept in sync by hand

"What counts as the same name, and how tiers/time_blocks are cohort-scoped" is a rule that must agree between the preview snapshot (buildExistingSnapshot, feeding pure buildPlan) and the commit-time re-resolution (seedRecognitionMaps, ingest.js:650–669). Today it is written in two places, each carrying a comment insisting it scope "EXACTLY as" the other so the two layers "cannot disagree" (:646–649). That is a hand-maintained coupling: correct now, drift-prone on the next entity or scoping change.

Deletion test: a shared recognitionKey already exists and is used on both sides — the gap is the scoping/enumeration around it. A single buildRecognitionMaps(db, camp_id, cohort_id) (or a shared scoped-entity descriptor) consumed by both the snapshot and the commit path makes the "cannot disagree" invariant true by construction instead of by comment. Complexity concentrates in one place.

Medium because the two paths genuinely need different outputs (a snapshot vs. a name→id-set map), so the shared piece is the scoping rule, not the whole function — a smaller, well-bounded extraction.

Explicitly not flagged

  • The renderer computing buildReconciliationReport. It runs in the renderer but is pure and fed entirely by the IPC dry-run result — no SQL, no IPC detail, no React state crosses into it. This is correct placement, not seam-misplacement.
  • The dozen ADR-slice comments in ingest.js. Dense, but they are load-bearing rationale (why a gate is ordered as it is), not dead narration. Out of audit scope (style) and genuinely useful.
  • importAliasScope.js (8 lines), importOutcomeModel.js (35 lines). Small pure constants/helpers, not shallow pass-throughs — deleting them scatters a shared constant across call sites.
  • Large pure parsers (extractEntities, textGrid, buildPlan). High line counts, but single-purpose behind narrow entrypoints and React/IO-free. Depth-as-leverage says leave them.

Bottom line

A large, recently-built subsystem that comes back with only two real structural targets — a decomposable write function and one un-modelled god component — is a strong signal of underlying health, stronger than a clean re-audit of a mature area would be. The pure decision/projection spine is a second benchmark alongside the schedule engine. The write path (C1, C3, C4) is the durable work and is orthogonal to the in-flight UI redesign; the component work (C2) should be reconciled with the active one-screen initiative before it is touched.
