# Run: Sweeps PR E — a rollback module for v72

> Written **before dispatch** per `WORK_RECORD_STANDARD.md` §5.1, and updated as agents return.
> A run abandoned halfway still leaves this file, which is the case where it is worth most.

## Brief

**Product outcome:** a developer who has to walk a database back past schema version 72 has a
module to do it with, and that module does not destroy erasure tombstones on the way.
`electron/db/rollback/` no longer has a hole at v72 — the one hole
`docs/work/tickets/T269-rollback-module-identity-guard.md` named explicitly while declaring
completeness out of its own scope.

**Success predicate:** `electron/db/rollback/v72_down.js` exists; it exports `rollbackV72(db)`;
its CLI self-guard is `endsWith('v72_down.js')`; it deletes `schema_migrations` rows
`WHERE version >= 72`; it drops **no** table; both identity guards
(`bareEqualityRollback.guard.test.js`, `rollbackIdentity.guard.test.js`) pass with it present;
`electron/db/rollback/v72_down.test.js` was red before the module existed and green after; and
every named gate exits 0.

**What does not count as done:**

- Dropping `tombstones`. `electron/db/schema.sql` creates that table unconditionally on every
  open, so a DROP would destroy signed purge tombstones the accepted ADR requires to propagate,
  and the table would come back empty on the next open — data loss for no rollback benefit.
- Editing `electron/db/localDb.js`, `electron/db/schema.sql`, or any migration block.
- A new schema version, a ticket number, or a status flip.
- A module the identity guards reject, or one whose test passes without ever having failed.

## Findings carried forward

- Two places on main assert, in prose, that v72 has **no** rollback module: the comment at
  `electron/db/localDb.js` inside the v78 guard paragraph, and the `schema_migrations` bullet in
  `docs/current/PLATFORM_STATE.md`. Both become stale the moment this lands. This PR is forbidden
  from editing `localDb.js`, and does not touch `PLATFORM_STATE.md`, so both are handed up rather
  than fixed. Neither sentence is load-bearing for behaviour: the tripwire it appears in was
  already resolved and now detects landed versions by version number, not by rollback-file
  presence.
- The remaining rollback-module holes (v27–29, v33, v48–50, v52, v54–58, v60, v61, v65) are
  untouched. Only v72 was in scope for this sweep.
- **Round 2, Red Hat HIGH finding, confirmed and now addressed in this module's own header/CLI
  text (not fixed in source — forbidden from touching `localDb.js`):** `electron/db/localDb.js`'s
  v73 forward block (guard `>= 72 && < 73`, T241) rebuilds nine tables using an explicit
  enumerated column list rather than `SELECT *`. Rolling a database's marker back below 72 (this
  module, or `v73_down.js` alone) and then reopening the app re-fires that block, because the
  guard window is exactly where the rollback leaves the database. `activities.catalog_role`
  (added later, by v75) is absent from v73's column list, so the rebuild silently drops it; v75
  then re-adds it as all-NULL. No error, no log line — a camper's ingest classification
  (`docs/adr/2026-09-26-ingest-category-exclusivity-and-anchor-identity.md`) is lost. Pinned by
  a new KNOWN-GAP test in `electron/db/rollback/v72_down.test.js` that reopens the db via
  `openLocalDb` after the rollback and asserts the column reads back `null`. This is a defect in
  `localDb.js`'s v73 block, owned by the owner to fix (rebuild from the live
  `table_info(activities)` column set, or an equivalent), not something this rollback module can
  or should paper over.
- **Stale comment, same root cause:** `electron/db/migrationDomainState.js`'s note on the v73
  entry ("every table rebuild is a straight SELECT * copy") is false — the code enumerates
  columns by name. That comment is part of why the column-loss hazard above was easy to miss; it
  should be corrected when the v73 block itself is fixed.
