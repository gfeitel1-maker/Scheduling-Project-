# Run: T267 PR2 — id-based cutover for fixed/recurring events

> Written **before dispatch** per `WORK_RECORD_STANDARD.md` §5.1, and updated as agents return.

## Brief

**Product outcome:** A pinned fixed/recurring event (e.g. Lunch at noon) and its
catalogue activity become the same row wearing two hats — linked by a stored
`activity_id`, not by matching spelling. Renaming in one place renames everywhere;
the free-choice catalogue never shows a pinned event; the event appears on the
generated grid exactly once per group per day; and if the app cannot tell which
activity a pinned event refers to, it says so loudly and refuses to generate
rather than silently placing nothing or placing it twice.

**Success predicate (from the ticket DoD + ADR §"specific predicate", all pinned by tests):**
1. A fixed OR recurring event resolves to **exactly one** activity. Zero and 2+
   are BOTH failures and BOTH surfaced (finding), never a silent `[]`.
2. The event appears on the generated grid **exactly once per group per day**
   after the change (T62 double-placement guard).
3. The name-matching fallback (`anchorNameKey`, `indexActivitiesByName`, name
   branch in `resolveAnchorActivityIds`) is **deleted**, not kept as a belt.
4. `activities.catalog_role` is the single authority for "is this row pinned".
5. Runtime WRITE paths set `fixed_events.activity_id`: `electron/ops/ingest.js`
   `commitPlan`, and the Anchors screen create/rename path — plus `catalog_role`
   set in the same commit; free-choice pickers / elective offering pool filter on
   `catalog_role IS NULL`.
6. `electron/ops/electiveRunOuterSchedule.js` `resolveTemplateSlot` returns the
   real `activityId` for an anchor (was `null`).

**What does not count as done:**
- A rename with resolution still by name (that is explicitly "not this ticket").
- Keeping the name fallback "just in case".
- Passing a hand-built fixture that assumes `activity_id` exists — the T62 scar.
  Fixtures MUST be built through the real `commitPlan`/`applyWrite` write path.
- Any PR3 cosmetic rename of remaining `anchor_activities` identifiers, or any
  change to the `events` table / Events screen. OUT OF SCOPE.
- A partial gate. Done requires full `npm run verify` green.

## Rounds

### Round 1

Maker implemented all six changes + the useGeneration refuse gate (test-first). Review panel
(Verifier deferred to the full gate; Red Hat, Code Reviewer, Tester foreground) then ran.

**Review findings and disposition:**

- **HIGH (Red Hat) — bulk import created N duplicate catalog activities.** `AnchorsScreen`
  `confirmImport` looped calling `resolveActivityLink` against stale React state, so a multi-day
  recurring import (Mifkad Mon–Fri) created 5 duplicate "Mifkad" activities — reintroducing the
  same-name drift class T267 exists to close. **FIXED:** `confirmImport` now seeds and mutates a
  local `activityCache` in-loop (mirroring `ingest.js`'s `activityIdByName`); test pins 5-day import
  → exactly 1 activity, all rows share its id (red-before 5→1).
- **MEDIUM (Red Hat) — ANCHOR_IDENTITY_GAP findings collapsed to one dismiss/React key** (both
  groupId/activityId null). Director dismissing one hid the rest. Refuse gate itself was unaffected
  (reads raw findings). **FIXED:** `findingKey.js` + `ScheduleScreen.jsx` now fold `anchorId` into
  the key for this kind; tests pin distinct keys per anchor.
- **MEDIUM (Code Reviewer) — 2+/ambiguity branch untested.** The UI ambiguity-throw path had no
  test. **FIXED:** added `AnchorsScreen.test.jsx` test that a 2+-name match refuses the save with no
  bare/null activity_id write.
- **LOW (Code Reviewer) — ingest duplicate-name handling is first-write-wins**, asymmetric with the
  UI's throw. **ACCEPTED DEVIATION:** duplicate-named catalogue activities are a rare pre-existing
  edge this PR did not introduce; first-write-wins matches every other name map in `ingest.js`. Not
  fixed by design; recorded here per WORK_RECORD_STANDARD §2.
- **LOW (Red Hat) — the ">1 match" finding branch is unreachable** because `activity_id` is a single
  scalar column, so `resolveAnchorActivityIds` returns 0 or 1. **ACCEPTED:** the guard is kept
  defensively and reads honestly (comment in buildSchedule.js); the "2+ = visible failure" half of
  DoD 1 is enforced UI-side (ambiguity throw, now tested). Noted, not removed.
- **LOW (Code Reviewer) — orphaned activity if the fixed_events write fails after activity create.**
  Two IPC calls, not one transaction. **ACCEPTED (pre-production, low-probability); not fixed.**
- **Note (Code Reviewer) — ADR test-plan items 6 (cross-device conflict on `activity_id`) and 7
  (mock allowlist drift tripwire).** Item 6 falls out of the existing per-field CRDT model with no
  new code (ADR lines 259–266); item 7's mirror is kept honest by
  `electron/ipcSurfaceParity.test.js` (already present). Neither is a new-code obligation for PR2.
- **Tester:** both director-facing error paths (ambiguity save-refusal; refused generation) are
  legible and use existing primitives (S.errorBanner, findings rail). UX 4/5, Visual 5/5.

All actionable findings fixed. Next: full `npm run verify` (Verifier adjudicates raw output) → Grader.
