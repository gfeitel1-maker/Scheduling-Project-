# Elective-run residuals round 2 — design note (parts 1+2 of q-elective-residuals-round-2)

**Design only — no code this pass.** Two director-facing defects at the elective-run commit seam
make a camper read as having gotten "one of their choices" when they did not. Both touch the
assignment↔preference join. The obvious fix for part (2) would change assignment-write behaviour an
earlier round set **deliberately to close a real outage**, so the organizer rules on the option and
surfaces the tradeoff to the owner if the pick reverses that fix.

## The prior outage fix this note must not blindly reverse

**`commitElectiveRun`'s assignment loop stopped throwing on a tier-uncovered fallback placement**
(T318, PR #663, commit `f6c4014a`, [electron/ops/commitElectiveRun.js:808-820](../../../electron/ops/commitElectiveRun.js)). The solver's `attends` predicate does not gate placement by tier, so a camper whose sheet division matched no group is routinely fallback-placed into a bundle-claimed occurrence their own tier cannot resolve. The first cut *threw* there; against the real acceptance fixture that **failed the whole commit — an ordinary roster gap became a director-facing outage.** The fix keeps the placement and emits a `BUNDLE_TIER_NOT_COVERED` finding instead. #683 (`715e1f60`) then bound the assignment's `choice_id` to the on-demand flat choice minted for *ranked* bundle labels — but `labelsNeedingFlatChoice` is built from `parsed.preferences` only ([commitElectiveRun.js:563-570](../../../electron/ops/commitElectiveRun.js)), so an **assignment-only** placement (a label no one ranked) still, correctly, gets `choice_id: null`.

## Defect 1 — linked-bundle anchor mismatch (the last unjoined row; acceptance pin lands at 1, not 0)

A linked-bundle preference binds to the occurrence of the **cell where its label appears on the sheet**, while the bundle's *assignment* is anchored at **another occurrence of the same bundle**. The join is by `(camper_id, choice_id, occurrence_id)` ([camperElectiveWeek.js:184-192](../../../src/screens/elective/run/camperElectiveWeek.js)); preference-occ ≠ assignment-occ, and the `(camper, choice, null)` fallback misses too (the preference is indexed at its own occurrence, not null). So a camper who ranked the bundle **#1** has `preference_rank` on the assignment but no `rankKind` from the join, and `rankLabel(rank, undefined)` returns the non-ordinal `UNORDERED_RANK_LABEL = 'One of their choices'` ([camperElectiveWeek.js:82-89](../../../src/screens/elective/run/camperElectiveWeek.js)) — a rank-1 request read as "one of their choices". Root cause: the join has no way to know the bundle's anchor occurrence. Measured: `origin/main` 4 unjoined rows → this tree 1; that last 1 is this defect (run record [2026-10-01-elective-run-residuals-from-683.md:130-137](../runs/2026-10-01-elective-run-residuals-from-683.md)).

**Options.** (1A) **Read-side anchor resolution (recommended).** Read `elective_choice_offerings` in `getElectiveRun` to recover each linked-bundle choice's anchor occurrence, and thread one field through the three `buildPreferenceLookup` call sites ([runStateCopy.js:452](../../../src/screens/elective/run/runStateCopy.js), [exportRunSummary.js:49](../../../src/screens/elective/export/exportRunSummary.js), [camperElectiveWeek.js:222](../../../src/screens/elective/run/camperElectiveWeek.js)) so the lookup also indexes a bundle preference under its anchor occurrence. **Read-only — does not touch assignment-write, so zero outage risk.** Cost: a contract change across 3 sites + 1 new read. (1B) **Occurrence-agnostic fallback** — add a final `(camper_id, choice_id)` match ignoring occurrence. One file, but it mis-ranks any choice legitimately offered at two occurrences with different ranks, and still needs the offerings read to scope itself to bundles — so it buys little. (1C) **Re-anchor at write time** in `commitElectiveRun` — changes the outage-sensitive assignment/preference write seam and risks the bundle's period semantics. **Recommendation: 1A, confidence high** — it is the only option that is both precise and entirely off the assignment-write path.

## Defect 2 — assignment-only mismatch persists with a null identity (F4), and the readout counts it as satisfied

Two coupled facets, one shared cause (`choice_id: null` on an assignment-only placement):

**2-i, persistence collision.** Two assignment-only mismatches for **one** camper on **two** different bundle labels both carry `choice_id: null`. The persisted finding id `deriveElectiveRunFindingId(runId, gen, 'BUNDLE_TIER_NOT_COVERED', camperId, choiceId, null)` ([deriveElectiveRunFindingId.js:45-54](../../../electron/ops/deriveElectiveRunFindingId.js)) is then **identical** for both (same camper, same null choice) — the second write collapses into the first and **one mismatch is lost from `elective_run_findings`**. In-session the response still has both (`noteMismatch` dedupes on `${camperId}::${labelKey}`, [commitElectiveRun.js:496-501](../../../electron/ops/commitElectiveRun.js)), so the loss only shows on **cold reopen**. Pinned by the F4 tripwire ([commitElectiveRun.bundleChoices.test.js:603-648](../../../electron/ops/commitElectiveRun.bundleChoices.test.js), asserts the wrong `toHaveLength(1)`); root cause in-code at [commitElectiveRun.js:978-991](../../../electron/ops/commitElectiveRun.js).

**2-ii, readout conflation.** Independently of persistence, the satisfaction readout counts a null-`choice_id` row as "got one of their choices". `buildPreferenceLookup` returns `null` for any row whose `choice_id` is null ([camperElectiveWeek.js:190](../../../src/screens/elective/run/camperElectiveWeek.js)); `satisfactionSummary` ([runStateCopy.js:456-480](../../../src/screens/elective/run/runStateCopy.js)) and `exportRunSummary` ([exportRunSummary.js:53-58](../../../src/screens/elective/export/exportRunSummary.js)) then take any row with a non-null `preference_rank` and a null `rankKind` as an **unordered-but-satisfied** placement — the same `UNORDERED_RANK_LABEL = 'One of their choices'` bucket as a camper who genuinely chose an unordered set. "We could not match this placement to any choice they made" and "they chose these as a tie" are rendered identically. This is the exact path Defect 1 also falls through (a join miss yields a null `rankKind`), so the two defects share this readout symptom; the on-screen copy tests at [runStateCopy.test.js:87-122](../../../src/screens/elective/run/runStateCopy.test.js) feed rank-without-choice_id rows but do **not** pin which bucket they land in — it is currently unguarded.

**Options.** (2A) **Finding-side identity fix (fixes 2-i; recommended).** Make the persisted finding id unique per `(camper, label)` — the key `noteMismatch` already dedupes on — instead of per `(camper, choice_id)`: derive it from a stable `labelKey` discriminator when `choice_id` is null (bump `deriveElectiveRunFindingId`'s version; findings are re-derived per `solver_generation`, so no migration). **Does not change the assignment's `choice_id` — zero outage risk.** Flip the F4 tripwire to `toHaveLength(2)`. (2B, fixes 2-ii; recommended) **Split the readout bucket.** In `satisfactionSummary`/`exportRunSummary`, a non-null-rank row whose preference join returned null is **not** "one of their choices" — count it as a distinct "placed, not from a ranked choice" (or fold into the existing not-requested/outside line). Read-side only; zero outage risk; guard it with the copy test 2-ii notes is missing. (2C) **The "obvious" fix — pre-scan assignments into `labelsNeedingFlatChoice`** so a flat choice is minted for unranked labels. This removes the 2-i collision *but* changes the assignment loop's `choice_id` write for a fallback placement — giving a label the camper **never ranked** a real `choice_id` the readout would then render as a ranked choice. That **reverses the outage-era `null` decision** (null = "they never ranked this") and moves the acceptance numbers. **Recommendation: 2A + 2B, confidence high.** Reject 2C: it is the only option that reverses PR #663/#683's deliberate `null`; if the owner wants it, it is his call, not a default.

## Summary

All of this is fixable **entirely on the read/finding side**, leaving the outage-era assignment-write (`f6c4014a`) untouched: **1A** (anchor resolution via `elective_choice_offerings` + a threaded field through the three `buildPreferenceLookup` call sites), **2A** (finding id keyed per camper+label, not per null choice), and **2B** (the satisfaction readout stops counting an unmatched placement as "one of their choices"). The only option that reverses the prior outage fix is **2C**, explicitly not recommended and flagged for the owner's call. Confidence high; the weak point is 1A's contract-change surface (3 call sites + a new read), inherent to the join lacking the bundle anchor, not a design shortcut. Suggested build order: 2A + 2B first (small, self-contained, closes the director-facing "one of their choices" symptom for the common assignment-only case), then 1A (the larger contract change) to recover the exact rank on the anchor-mismatch row. This note becomes the build brief once the organizer rules.
