# Shoresh remembers every import answer in the camp document and learns patterns from them

## Owner request (2026-10-11, verbatim)

> "this question spot - what something is classified as, or if someone meant to not add something for a group, is the place where our machine or software learning should be coming in so that on a reimport or a new import with similar circumstances it is more confident. beyond that make sure that this is applying to fixed events as well. and all types of activities, or events."

> 2026-10-11, on the first draft (a device-local cache): "how does our machine or software learning kernel idea happen if it always forgets?"
>
> 2026-10-11, rulings: "i think we should lower the threshold for pattern matching to 3 examples, instead of 4. and i thiink that with the learning there needs to be a way to for a director or a staff member to see it in the same section but under it's own label where the devce storage is"

**Success predicate.** (1) Import campB (`docs/work/specs/samples/campB-by-day.txt`), answer N questions, re-import campB: zero repeat questions; every remembered answer is applied and labelled "Remembered from your answer on <date>". (2) A variant file (a renamed day or time, an extra group) with matching circumstances: remembered answers apply, only genuinely new patterns ask. (3) Changing an answer later updates the memory. (4) Works for every entity kind: activity, fixed event, recurring event, special event, elective. (5) Answer on device A, recall on device B. (6) Survives host handoff, device replacement and backup. (7) A new season (the same camp, re-imported) inherits it. (8) After 3 similar answers a deterministic, explained pattern pre-answers the next one.

**Non-goals.** No ML, embeddings or opaque model; no cross-camp learning. No new question kinds beyond the one classification affordance below. No change to what the engine infers. No migration of the five existing device-local memory tables (they coexist).

**Two corrections to the brief.** (a) `open_reconciliation_decisions` (`electron/ops/openReconciliationDecisions.js:78`) is a list of UNRESOLVED questions, deleted-and-replaced per commit. It is not an answer memory and nothing should be built on it as one; it only supplies the *content-addressed id idea* (`decisionId` / `fixedEventDecisionId`, `reconciliationReport.js:60,228`). (b) `import_decisions` (`electron/ops/decisionJournal.js`, `src/ingest/decisionJournal.js`) records what was asked and answered, per import, but stores compact `proposed`/`chosen` JSON with **no decision id and no signature**, so it cannot be replayed. It does reserve `seedling_key` and `learned_from_id` (`electron/db/schema.sql:266-280`), both NULL "until slice 3". This ADR is that slice.

**The structural finding.** A positive answer to a "create" question leaves the entity in the database, so the next plan sees it as `unchanged` and never asks. Memory is needed where an answer leaves no trace in entity state: `keep`, `decline`, `as_written`, "not an event", acknowledged drift, and a file's re-presented pattern (all-camp exclusion). A positive answer is still *evidence for learning* (3.4), though not instance memory.

**What the archived seedling spec decided that still binds** (`docs/archive/completed-specs/2026-09-15-seedlings-importer-learning-design.md`, the owner's original "kernel / nugget / seedling" ask: "stop needing a human for obvious cases through a learning process"). It was archived only because eight real workbooks then produced zero questions, so there was nothing to learn from. That premise has flipped: #873 and #889 surface 41 questions on campB. Carried forward: **Invariant 1** (learning may promote only what is held for *uncertainty*, never what is held for *authority*: `all_camp_override` and `elective_candidate`); **Invariant 2** (a pattern the director keeps correcting stops being applied and the question returns); **Invariant 3** (recall can only fail toward asking); no model, no embeddings, and every recalled answer answers "why did you think that?" with a sentence; no cross-camp learning. Changed: the archived design stored mutable counters in a host-local table; this design is durable (camp document) and derives every count from grow-only answer records.

## 3. Decision

### 3.1 Storage: per-answer records in `camp_seedlings`

No new SQLite table. **Schema v95 is not needed and no rollback module is needed**: the projection exists (v82), `status` allows `active|superseded`, and `idx_camp_seedlings_lookup (camp_id, kind, status)` exists. (If implementation proves a column unavoidable, that is a new decision: take v95 then.)

- **Id.** `deriveCampSeedlingId(campId, kind, matchKey)` (`electron/ops/electiveDerivedIds.js:397`) with `matchKey = <key_hash>-<answerUuid>`; a fresh uuid per answer, so no two answers share an id. The `key_hash` prefix lets recall find all answers to one signature by `match_key LIKE '<hash>-%'`. Ids are never parsed (the module's own prohibition, `electiveDerivedIds.js:70-73`); the kind is read from the `kind` column.
- **Columns used** (all exist): `camp_id`, `kind`, `match_key`, `payload`, `status`, `confirmed_by` (user id), `confirmed_at`.
- **`payload`** (JSON, immutable once written): `{ v, qkind, role: 'instance'|'evidence', seq, import_id, parts, baseline, refs, camp_shape, features, answer, supersedes: [ids], overrode: [ids], covers: [ids] (vetoes only), bulk? }`. **No display names and no camper data.**
- **Whole value, per #884, for ALL `camp_seedlings.payload`.** Add `'camp_seedlings.payload'` to `WHOLE_VALUE_FIELDS` (`electron/automerge/campDocument.js:539`). Decision on the column-mapping payloads: **they switch too**, not kept as plain strings. A kind-aware exception would need the writer to parse the derived id, which `electiveDerivedIds.js:70-73` forbids; the mapping payloads are small header text, the readers already take either form (`plainValue` at the document accessors, and SQLite holds a string), and `recallColumnMapping` is unchanged. A test asserts a column mapping written before and after the change both recall.
- **Minimum peer version.** The first build containing #884 (`13b36d6e`); no tag contains it, and the sync layer has no version negotiation (I found no peer-version constant in `electron/sync`). A build that cannot read a `camp_seedlings` payload logs one startup line (`camp_seedlings: N records this build cannot read`) rather than failing silently. A pre-#884 peer cannot project an `ImmutableString` field; I have not verified whether it logs a projection failure or throws, so verify on a pre-#884 build if any such device exists. The project is pre-production with no live users, so the cutover is "update every device", the same cutover #884 already imposed for schedule snapshots and map images.
- **Writes** go through `appendOp` inside one `runAtomic` (`rememberColumnMapping.js:61-68`). After a camper purge, `seedAllFromSqlite` regenerates the document (`electron/automerge/purgeSupportCommand.js` ~l.340-372); a test asserts the regenerated payload is still an `ImmutableString`.
- **Generic consumers of `camp_seedlings`** (grep of `src/`, `electron/`, `scripts/`, excluding tests) and how each handles the new kinds:

| Consumer | Handling |
|---|---|
| `src/screens/elective/assignment/AssignmentPanel.jsx:599` (`list('camp_seedlings')`, admin-only screen) | `recallColumnMapping` skips any `kind !== 'preference_column_roles'` (`mappingSeedling.js:191`); unchanged. Test 13. |
| `src/localClient.mock.js:617,1861` | mock field list unchanged; add mocks for the new IPCs; `rememberColumnMapping` mock filters by id only. |
| `electron/main.js:775-796` `rememberColumnMappingHandler` | unchanged; the new handlers are separate. |

| `electron/db/localDb.js` v82, `rollback/v82_down.js`, `v85_down.js`, `migrationDomainState.js:113` | table lifecycle and comments only. |

- **History: Change, supersede, Forget (causal, not clock).** Change references what it replaces: in one `runAtomic` the writer sets `status='superseded'` on **every live record for that `key_hash` visible to it**, then inserts the new record (fresh id) with `payload.supersedes = [all those ids]`. "Remember this" on a baseline-mismatch near does the same (same `key_hash`); on a `name_key` near (different key) it only inserts. Forget = `status='superseded'` with no live successor. Same answer re-confirmed = write nothing. Concurrent Changes on two devices each supersede the same old record and leave two live heads; a third Change on a device that has seen both supersedes both (test 10). Missing ids in `supersedes`/`covers` (deleted by retention) are ignored.
- **No UNIQUE index.** A unique constraint on a replicated projection can fail at merge time, so live uniqueness is the writer's job (above) and recall resolves concurrent heads deterministically: heads that agree are one answer; heads that disagree are a contradiction (the card is NEAR and the disagreement is counted).
- **Growth.** About 8 ops per record (7 fields plus one payload op), roughly 0.5 to 1.5 KB. campB's 41 answers cost a few hundred ops. Nothing is written when an exact recall is left alone or an answer is re-confirmed; counts are derived, never incremented; the writer deletes superseded or forgotten records older than 180 days beyond the newest 2 per `key_hash` (document history keeps the bytes, as for any delete); a hard cap of 5,000 records per camp stops new `evidence` rows (never instance answers). A test covers retention delete versus a concurrent edit from an offline peer: delete wins, the peer's edit to the deleted record is lost, and any later `supersedes` pointing at it is tolerated.

### 3.2 Trust model: validate at read, count only qualifying authors

A camp peer can write any `camp_seedlings` field (the receive side does not re-authorize per merge for ordinary entities, `docs/current/CRDT_SECURITY_GAPS.md`, accepted 2026-09-08). So **nothing in the document is trusted until it is validated at READ.** One module-level function, `liveRecords(db, campId)` in `electron/ops/answerMemory.js`, is the only reader of these kinds; recall, patterns, explanations, the per-import summary and the Settings view all call it, and a guard test fails if any other file selects `kind IN ('import_answer','import_rule_veto')`.

1. **Schema.** A strict validator per record: `kind` in the frozen allow-list; `payload` is a string of at most **4 KiB**, checked BEFORE `JSON.parse` (the cap is enforced at read, because a peer controls what was written); the parsed object may contain only the frozen key allow-list above, each with type and length bounds (id arrays at most 64, `parts` at most 16 entries); `qkind` from an enum; `answer` must pass that qkind's own answer-shape validator; `seq` a plain integer in 1..2^31-1 (**no count-based cap**: a cap tied to the number of records would silently discard the newest answers after a retention pass deletes old ones). Anything else is discarded whole and counted in a diagnostics tally (not shown to the director unless nonzero in the Settings view footer).
2. **Authorship counts.** A record counts toward **auto-apply and pattern support** only if its `confirmed_by` resolves, **at recall time**, to a live user who currently holds `groups.import`. Records from anyone else are treated as NEAR-only (pre-select, ask), never count as support, and are labelled **"as recorded"**, because `confirmed_by` is a claim in the document, not a signature. The same applies to Tier-0 exact auto-apply.
3. **Peer-forgery risk: accepted, with bounds, not closed.** A malicious *already-approved* device can write a record claiming a live importer's `confirmed_by`. Bounds: it needs an approved device; it cannot make an authority kind auto-apply (3.4); it cannot write entities, only pre-answer questions of one decision kind visibly; every auto-applied answer is listed on the review screen with "auto-applied: N" and an undo, and in the Settings view with its record. Closing it fully means signing records with a device or host key (the tombstone mechanism, `verifyTombstone`); rejected for v1 as the same forgery already exists for every ordinary camp entity. Revisit trigger: any real second operator with an approved device that the director does not control.
4. **Shared exclusions.** `liveRecords()` also drops records whose `refs` contain an id present in the `tombstones` table, or whose alias refs point at a tombstoned `source_aliases.entity_id`. This runs at read, so a record that arrives **after** its tombstone is excluded just the same.

### 3.3 Permissions

`camp_seedlings.write` stays admin-only for column mappings (`electron/auth/permissionsEntityParity.test.js:63`). Staff with `groups.import` import and answer (2026-10-09), so: **two new actions, `import_answers.write` (the roles that hold `groups.import`) and `import_answers.read` (every signed-in role)**. The handler writes only the two allow-listed kinds, so staff cannot write a `preference_column_roles` record through it; the parity test's `camp_seedlings` reason is amended to carve this out. Alternative (admin-only writes) would leave staff answers unremembered.

### 3.4 Instance memory (Tier 0) and patterns (Tier 1)

**Tier 0 is unchanged from the first Red Hat round.** `signatureOf(decision) -> { qkind, parts, baseline, refs }` is pure (`src/ingest/answerMemory.js`); the key is built in ONE server-side function. Rule: `parts` are what the answer provably depends on; `baseline` snapshots whatever cannot be proven irrelevant; **any baseline mismatch downgrades EXACT to NEAR**. Normalizers: names `normalizeName` (`src/ingest/preview.js:14`), deliberately NOT `whitespaceInsensitiveName` (`:23`; "Lunch 2" and "Lunch2" stay distinct, as in `confirmAlias.js:78`); days `canonicalDay`; blocks as `start-end` minutes (`src/ingest/blockTimeText.js`); sets sorted and JSON-encoded; parts over 64 characters replaced by `h:` + the full SHA-256, never truncated. Ids are validated on recall (live, name still equal, same active alias row), else NEAR.

| qkind | Questions | `parts` (exact key) | `baseline` (mismatch -> NEAR) | Left out, and why |
|---|---|---|---|---|
| `classify` | fixed-event `confirm_value`, weekly recurring, `elective_candidate`, "is this an activity" | name, proposed class, day set, block minutes, group scope | location id, groups present for the cohort, group count | file name, sheet, import time, row order, formatting: none feed `fixedEvents.js:200-260` |
| `exclusion` | `all_camp_override` | name, sorted EXCLUDED group ids, day, block minutes | **attending set**, `occurrences`, `insteadByGroup` | `totalGroups` (derived) |
| `value` | `confirm_value` `edited`; `confirm_change` | entity id, field list, hash of offered `to` | **stored value at answer time** | offered `from` |
| `drift_ack` | fixed-event moved / scope drift | name, from, to | stored slot at answer time | none |
| `split` | accepted two-row split | name | the two patterns' days and blocks | none |
| `merge` | name-variant, multi-block | sorted variant set | canonical target id | none |
| `residue` | unknown label, packed cell | label (hashed if long) | ids of candidate activities | none |

An extra attending group is NEAR (one confirming tap): it is in the exclusion baseline. See open question 3. Camper names never enter a signature: the writer refuses a part whose normalized text equals a current camper's normalized display name or external id.

**Tier 1 patterns are computed at recall time from the validated records** (`src/ingest/answerPatterns.js`); nothing extra is stored.

*Features* (pure, frozen, versioned `FEATURES_V = 1`): `stem(name)`, `isMeal(name)`, `dayShape` (`daily`/`weekly`/`single`, from `fixedEvents` `basis`), `scopeShape` (`all` vs subset), `blockLenClass` (`short` under 30 minutes, `standard` 30 to 59, `long` 60 or more, constants in `LEARNING_BAR`), `excludedSet`, `proposedClass`.

*`stem()` limits, documented and tested.* It strips only a trailing numeric token, reusing `numberedBase` (`src/ingest/fixedEvents.js:303`) and the stem logic in `src/ingest/inferDivisions.js`, exported rather than re-spelled. So "Lunch 1/2/3" share the stem `lunch`; "Group 2A" and "Group 1b" do **not** (alphanumeric suffix: no pattern, which fails toward asking); "Period 2" and "Period 12" **do** share a stem and would be treated as siblings, guarded only by the baselines below and by demotion on a contradiction. A stem under 3 characters, or one that still contains a digit, forms no pattern.

*Templates: a fixed menu, never a search.*

| Template | qkind | Antecedent (all equal) | Example |
|---|---|---|---|
| T1 numbered siblings | `classify` | proposed class + `stem` | Lunch 1 to 3 answered "fixed event" -> Lunch 4 |
| T2 meal | `classify` | proposed class + `isMeal` | Lunch, Menucha 2, Snack |
| T3 same exclusion | `exclusion` | `excludedSet` (any activity) | "all camp except CIT" for 3 activities -> the 4th |

`isMeal` is **the anchored whole-name test only**: the existing `MEAL_NAME = /^(lunch|menucha|breakfast|dinner|snack)(\s*\d+)?$/i`. It is currently a function-local constant at `src/screens/reconciliationResolutions.js:159` (there is no `MEAL_NAME` in `fixedEvents.js`); it is moved to a shared module and imported by both, one definition. **Note on value:** an unanswered meal-named fixed event already imports (`reconciliationResolutions.js:158-163` keeps `daily`/`weekly`-basis events and any `MEAL_NAME`; it holds only a sibling-basis non-meal such as "Specialty 4"), so T2 buys little; the **T1 numbered-sibling test is the meaningful one** and T2 is kept mainly as a non-collision guard. **TRANSPORT is dropped from v1**; the test prints campB's asked fixed-event names, and a transport class returns only if campB shows the need. Collision table (T2 `isMeal`): matches `Lunch`, `lunch 3`, `Menucha 2`, `Snack`, `Lunch2`; does **not** match `Snack Shack`, `Lunch Duty Volunteering`, `Dinner Dance`, `Bus Games`, `Pickup Basketball` (the last two are why no token-based transport class exists).

*Induction.* For a new decision and a template, take every **qualifying** record (3.2) whose antecedent equals the decision's, one per **distinct instance** (distinct normalized name for that qkind; the same activity across weeks or a re-import counts once), ordered by `(seq desc, id)`. `seq` is a Lamport counter: the writer sets it to 1 + the highest `seq` among the live records it can see for that qkind, so it is causal and clock-free (a forged huge `seq` matters only to a forger who also qualifies as an author, a risk already accepted in 3.2); `confirmed_at` is display and a last-resort tie-break only. A veto ignores exactly the answers in its `covers` list; answers it did not cover (for example arriving from a device that had not seen the veto) stay live.

*Bands and the bar* (constants in one frozen `LEARNING_BAR`; the bar is **3**, owner ruling 2026-10-11):

| Band | Condition | Effect |
|---|---|---|
| ESTABLISHED | at least **3 distinct instances** from at least **2 distinct imports** (`import_id`), the **3 newest agree**, and at least one supporter is an **explicit** record (`role:'instance'`): an **edited value or a decline on a non-recalled card**, or a "Remember as a pattern" tap made on a **non-recalled** card (on a recalled card the tap counts as agreement, never as the explicit supporter) | auto-apply (eligible kinds) or pre-select (all others) |
| SUGGEST | the 2 newest agree (including evidence-only support, or support from one import) | pre-select, still asks; the card offers "Remember as a pattern" |
| ASK | one example, or the newest disagrees with the one before | ask, no pre-fill |

`looks_right` evidence (`role:'evidence'`) may raise SUGGEST but **never ESTABLISHED on its own**. Evidence written through a bulk control is **excluded entirely** (`bulk: true`, counts toward nothing). Bulk means any `RootMapPanel` answer whose `onAnswer` covers **more than one decision id**, which includes the "Use the file's values for all N remaining" button (`src/components/reconciliation/RootMapPanel.jsx:303-305`) and any group-level answer: answering many cards at once is not a considered confirmation. Three `looks_right` records from one session therefore cannot establish a pattern: that is the failure this closes.

*Demotion and no single-override flip.* A newest answer that disagrees drops the pattern to ASK at once; recovery takes fresh agreeing answers (2 for SUGGEST, 3 from 2 imports plus an explicit one for ESTABLISHED). So **one override can never flip a pattern to the opposite auto-apply**: the opposite answer must clear the whole bar on its own.

*Baselines for patterns.* Each supporting example stores `dayShape`, `scopeShape` and `blockLenClass`. A new decision auto-applies or reaches ESTABLISHED only if all three equal the examples' (the dimensions the answer depends on: a daily lunch generalizes to a daily lunch, not to a weekly event or an hour-long block); **any mismatch caps it at SUGGEST**.

*Authority registry, keyed by decision kind, fail closed.* `AUTO_APPLY_ELIGIBLE` is a frozen allow-list of `(decision.kind, entity)` pairs, currently only `('confirm_value', 'fixed_events')`; T1 and T2 apply only to those. Everything else, including `elective_candidate`, `all_camp_override`, `elective_candidates_truncated`, `resolve_conflict` and any kind not listed, can reach SUGGEST at most, however strong the pattern ("only they know whether that group had a trip"). **Auto-apply only ever produces the ACCEPTING answer** (the one that takes the proposal: create or keep the proposed fixed event). A rejection, a decline, "Not an event", or anything that deletes or withholds stays at SUGGEST even when ESTABLISHED. A new decision kind is non-eligible until someone adds it; a test enumerates `buildReconciliationReport`'s kinds and fails on an unclassified one. An exact-instance repeat of an authority-kind answer (same activity, same exclusion, same day and block, baseline equal, qualifying author) still auto-applies: memory of one decided question, not promotion by history.

*Explanation.* Sentence from the examples, counted over **all** qualifying live records, not just the window: "You answered **Fixed event** for Lunch 1, Lunch 2 and Lunch 3 (Dana 3 Jul, you 12 Oct). Lunch 4 is the same kind of thing. **Established**: 3 agree, 5 earlier disagreed." Up to 3 names, then "and N more". Confidence is words plus counts, never a percentage. Each shows Change and Forget this pattern. Labels read "as recorded" for non-qualifying authors.

*Positives as evidence.* `looks_right` is written as `role:'evidence'` for qkinds with a template (`classify`, `merge`, `residue`) when answered one card at a time; never instance memory; shown in the view as "You confirmed".

### 3.5 Read path, write path, provenance, visibility

- **Read.** One site for the review queue: dry-run reconcile in `electron/ops/ingest.js`. `matchImportAnswers(db, campId, decisions)` calls `liveRecords()` and attaches `decision.recalled = { source: 'instance'|'pattern', match: 'exact'|'near'|'pattern', band?, memoryId, answer, examples?, answeredAt, answeredBy, asRecorded? }`. Tier 0 first. A recalled answer re-passes `isEditableDecision` / `isBackedConfirmChange` and the entity-live check. **Exact** seeds `answers[id]` through the same code as a click, so `isDecisionResolvedFor` and `applyResolutions` need no new branches. Near, SUGGEST and capped ESTABLISHED pre-select and still ask. Preview-time kinds call one IPC `matchImportAnswers({ signatures })` (gated `import_answers.read`). Replace mode recalls the state-independent kinds only. A memory not yet synced to this device simply asks: recall fails toward asking.
- **Write.** After a successful non-held commit, a sibling of `confirmRemembers` and `recordImportDecisions`: pure `answerMemoryCalls(decisions, answers)` -> `rememberImportAnswers` (gated `import_answers.write`; `camp_id` from the camp row; signatures recomputed and validated server-side; allow-lists). Fresh answers are written by default; answers on a NEAR card only through an explicit **Remember this** (default off); an exact recall left alone writes nothing; Replace-mode answers are written. A Change on a recalled card writes a record with `overrode` = the recalled ids.
- **Per-import "auto-applied: N".** The review screen shows "Auto-applied: N" with **"Undo for this import"**. Before commit it returns exactly those cards to unanswered for this import only; **no record is written and the pattern is not forgotten or demoted** (the journal records the outcome locally as `rejected`). The undone cards go into a **session suppression set** (in memory, this session only) that the matcher consults, so they are not re-applied when the screen re-renders or re-runs the dry run in the same session. After commit the existing grace-window "Undo this import" is the undo; a selective post-commit undo of only the auto-applied cards is not designed here. The first auto-application of a pattern in a camp is shown expanded.
- **Provenance.** "Remembered from your answer on 12 Oct" / "from Dana's answer on 12 Oct" (name read from `users` by `confirmed_by`; "a former user's" if absent; "as recorded" when the author does not qualify).
- **Visibility.** Every import shows "N answers remembered, review". The Remembered group is collapsed except cards whose `camp_shape` differs from the `last_shown_shape`, which expand with "Your camp changed since you answered". `last_shown_shape` is a per-viewer, per-device viewing state in `localStorage` (the `src/utils/setupReviewed.js:21` pattern), deliberately not replicated; missing means expanded.
- **Journal.** Recalled decisions are `ACCEPTED` with `import_decisions.learned_from_id` = the record id.

### 3.6 Erasure, privacy

- **What the 2026-09-19 ADR decided** (`docs/adr/2026-09-19-multi-device-erasure-propagation.md`, "The erasure guarantee", lines 233-247, re-read): **logical** erasure. A signed tombstone (id, version, signature; no name) gates projection so a purged record can never reappear; bytes may remain in each device's history; physical byte-erasure needs genesis rotation (break-glass) and is out of scope.
- **What `purgeCamperRecord` does** (`electron/automerge/purgeSupportCommand.js:197`): it purges one **camper**: deletes the camper-keyed rows (`elective_assignments`, `elective_preferences`, `elective_run_outer_snapshots`, `elective_run_findings`, `camper_identity_keys`, `campers`), mints the tombstone, and regenerates the document from SQLite. It does **not** scan free text in other entities, so it would not scrub a camper's name from `parts`/`features`. The guarantee therefore rests on construction: signatures hold only activity, event, group, location, day, time and class text; the writer refuses a part equal to a camper's normalized name or external id; a test scans every payload written from a campB import against the seeded campers' names. A director naming an activity after a child is the same exposure as the activity row itself, which purge also leaves.
- **Tombstones today** name only campers, and our records hold no camper ids, so tombstone exclusion in `liveRecords()` (3.2) is defense in depth for any future structural purge. A record arriving after its tombstone stays excluded because the check runs at read. No display names are stored, so an erased user shows as "a former user".

### 3.7 Settings-adjacent view: "What Shoresh has learned"

**Progress toward auto-apply (keeper, on GO).** Every pattern row shows how close it is to applying on its own, in the director's terms: "2 of 3 answers" (agreeing instances), plus the other conditions still missing ("needs one more import", "needs one answer you edited or declined"). For a kind that can never auto-apply (all-camp-except, electives, any rejection), the row says so plainly, e.g. "Always asks you: this kind only pre-selects", so the owner sees the learning grow and why those answers stop at a suggestion. Computed by the same recall code as the tiers, never a separate count.

**Where (corrected by the keeper).** The device-storage block is the sidebar footer in `src/components/layout/Sidebar.jsx`: "Backup now" (admin-only button, label at `:460`), "Show in Finder", `<RestoreControl />` (admin-only, `:477`; its text includes "Restore from backup…"), then the ungated "About & Legal · v0.1.0" button (`:480-492`). **"What Shoresh has learned" is a new, ungated, own-labelled footer entry placed directly under `<RestoreControl />` at `:477`**, so staff and directors both see it, and it opens the view. It follows the footer-only pattern of `about` and `pairAgain` (`src/App.jsx` SCREENS comments), not a nav stage and not the Settings gear menu.

**Blast radius.** A new `SCREENS` key (`learned`, `src/App.jsx:47`) fans out to several enumerator and guard files (for example `screenDestinationsExist.test.js`, the screen-key list, `TopBar` titles); only the full `npm run verify` finds them all, so the Maker brief must plan for it. The new action pair and the `Sidebar` change add the permission-parity test and the sidebar tests.

**Content.** Grouped by kind (Classification, "All camp except...", Values, Splits and merges, Other); within a group, learned **patterns** first, then **answers**; the five legacy device-local stores appear read-only as "Remembered on this computer only". Each row: what ("Lunch 1 to 3 are fixed events"), **why** (examples, dates, who), **confidence** (word plus counts, including earlier disagreement), **date and who answered** ("as recorded" where the author does not qualify), **Change**, **Forget**.

**Answers from people who no longer import.** The view shows a count ("N answers are from people who no longer import"). Each such answer, and the pattern it supports, is listed "as recorded" with a **Keep this answer** action: a current `groups.import` holder re-records it under their own name (a new record with fresh id, `supersedes` the old one, `confirmed_by` = the keeper), after which it qualifies. Keeping does not change the answer, only who vouches for it.

**Permissions.** View: `import_answers.read` (directors and staff). Change, Forget and Keep this answer: `groups.import`. Without it the controls are not rendered and a quiet line says "You can see what Shoresh has learned. Changing it needs import permission."

**Empty state.** "Nothing learned yet. When you answer an import question, Shoresh remembers it here, and starts to spot patterns after three similar answers."

**Long list.** Groups collapse with counts, 25 rows per group with "Show more"; a search box and a kind filter appear only past 15 rows (campB alone is 41); search matches name and example text.

**Forget semantics.** *An answer*: retired (`superseded`, no successor); that exact question asks again; patterns it supported are recomputed (may demote); nothing already imported is undone. *A pattern*: writes an `import_rule_veto` whose `covers` lists the ids of the answers it covered at that moment; the pattern stops pre-selecting and auto-applying; **the underlying answers are kept** (each exact question still resolves, and they stay listed); newer answers not in `covers` rebuild it only by clearing the whole bar again. *Change*: the same editor as the card; writes a superseding record (agreement or contradiction for patterns).

**Design standards.** Needs a **Designer pass before Maker** (DESIGN_STANDARD §5 and §8): Change, Forget and Undo are async (immediate pressed state, inline pending, result on the row; the reduced-motion equivalent is a text and weight change on the same element, never no feedback); expanding groups and the Remembered group are view transitions under §8 with the same rule; no banners.

### 3.8 Durability, backup and new seasons

- **Handoff, new device.** The records are in the camp document: nothing to hand over (`HANDOFF_TABLES` and `PURGE_WIPED_TABLES` unchanged; a guard test asserts `camp_seedlings` is in neither, because it re-projects) and a replacement device receives them by sync.
- **Backup and restore must round-trip the records, including forgotten and superseded state.** A backup is the pair `shoresh-<ts>.db` plus the camp `.automerge` document (`electron/db/projectManager.js:107,128`; `electron/db/backupRestore.js:20,57,88`), so both the SQLite projection and the document carry every `camp_seedlings` row with its `status`. Requirement and test: seed answers (live, superseded, forgotten, veto), back up, restore into a **fresh database for the same camp** (the state of a replacement device), and assert recall, the Settings view and the explanations are identical, and that a forgotten answer stays forgotten after restore plus sync with a peer that still holds the pre-forget state (causal `supersedes` and status win; nothing resurrects). **Restore refuses a backup from a different camp** (`backup_wrong_camp`, `backupRestore.js:41-47`), so memory cannot cross camps; "fresh camp" is therefore tested as a fresh device of the same camp, plus the negative that a different camp id is refused.
- **New season.** There is no new-season flow, and a new season is the same camp re-imported (keeper ruling 2026-10-11), so memory carries automatically through "Re-import last year" (`navSections.js:143`). **No carry slice** and no export/import file; the earlier carry design is dropped.
- **Coexistence.** The five device-local stores stay as they are (no migration) and are listed read-only in the view. They still forget on device replacement; see open question 5.
