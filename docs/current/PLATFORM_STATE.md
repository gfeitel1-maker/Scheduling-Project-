_Prior: 2026-09-18 (**T210, Phase B — the signed rendezvous record contract, and the camp
rendezvous namespace, schema v69. Pure library code, not wired into any running path.**
`electron/sync/automerge/rendezvousRecord.js` defines the canonical signed byte encoding
(`docs/adr/2026-09-18-rendezvous-record-encoding-and-namespace-rotation.md`): a fixed-order,
length-prefixed concatenation — never `JSON.stringify` — signed with the publishing device's own
libp2p Ed25519 identity key and self-verifying against the record's own `peerId`. `verify()` returns

way and never registered in `PROJECTIONS`/`campScopedEntities.js`/`MODELED_ENTITIES`. **Namespace
and epoch are ONE document key, not two** — a round-2 review finding (the ADR's Decision 3a):
Automerge's per-key conflict resolution would otherwise let two devices rotating concurrently merge
into a namespace/epoch pair neither device generated, and a director resolving what looked like two
unrelated conflicts could pick exactly that mix by hand. `rendezvousDiscovery` holds a fixed-shape
string `v1:<decimal epoch>:<64 hex namespace chars>`, strictly parsed — a malformed value throws
rather than half-parsing. **Nothing here is imported by `electron/main.js` or any production sync or
discovery path** (`INTERNET_TRANSPORT_SIGNOFF` stays `false`, the Tier-4 guard in
`electron/sync/automerge/transportBoundary.guard.test.js` is unmodified); wiring is T211 and remains
parked. Also fixed in round 2: the u64 wire fields (`epoch`/`seq`/`issuedAt`/`expiresAt`) now reject
a value above `Number.MAX_SAFE_INTEGER` on both encode and decode instead of silently rounding it
via `Number(bigint)`, and `verify()` rejects a record whose `expiresAt` precedes its `issuedAt` as
malformed rather than reasoning about an inverted freshness window. **Revocation limitation, stated
rather than assumed**: revoking a device stops IT from receiving further document state on the
revoking device's own connection (`electron/sync/automerge/transport.js`'s `revokePeer`), but no code
path tears down a THIRD device's connection to a revoked peer merely because the revocation arrived
through sync — that device keeps trusting the peer until its own trust check independently fires.

recorded rather than silently overridden. Prior header note follows.)_

Mitigation ADR `2026-09-14-users-auth-fields-off-the-replicated-document.md` is **accepted** (Host-signed credential fields: `role`/`pin_hash`/`pin_salt` keep replicating but carry an Ed25519 `auth_sig` the Host alone can produce, verified on projection — closes the attack without regressing offline login) and **in progress**. **Fully implemented** across primitives (`electron/auth/authSignature.js`), schema **v60** (`users.auth_sig` + Host-side backfill), minting at the only two credential-write sites (`createUser` + `promoteToAdmin`; `write()` now refuses generic `users.pin_hash`/`pin_salt`/`role` writes), and **projection-time enforcement** in `projector.js`'s `upsertUsersEntity` — which runs on the merge path only and refuses a credential *change* whose `auth_sig` does not verify, while always applying unchanged values and, when no public key is present (rebuilt device, #401), *skipping* the unverifiable change (keeping current values) rather than accepting it, so a forgery is never applied and no one is locked out. Independent `security-assessment` + `red-hat` review confirmed the primary Q1 escalation/overwrite attack closed. The two MEDIUM residuals the review found — signature **replay/rollback** and **degrade-window permanence** — are now also **fixed (T172)**, escalated from Tier-4 to present-risk because devices connect over paths beyond the LAN: a monotonic `cred_version` (schema **v61**) bound into the signature defeats replay, and a device with no verifying key now *skips* rather than accepts an unverifiable credential change (so a forgery can never be applied, while a legit value still lands once the key is present — `camps` projects before `users`). **Transport boundary (corrected 2026-09-15):** the production node binds all interfaces (`0.0.0.0`, `main.js`), not loopback; what keeps it off the internet today is mDNS-only discovery (no DHT/relay/bootstrap wired) — the Tier-4 guard now checks that real wiring, not a dead loopback constant. The owner has decided the next step is **cross-internet sync via direct hole-punch, no relay/server**; a WAN assessment (`docs/work/security/2026-09-15-wan-dht-boundary-assessment.md`) lists the must-fix blockers (40-bit non-rotating join code, LAN-sized rate limits, unsigned builds) and the networking invariant that symmetric-NAT/CGNAT pairs cannot be punched directly without a relay. At-rest encryption: **accepted** (ADR `2026-09-15-at-rest-encryption-scoping.md`) — app-level encryption of the SQLite db (SQLCipher-family) and the `.automerge` doc, keyed to the OS keychain, migrated behind a pre-migration backup; in progress. Blocker #1 (join code) is designed in ADR `2026-09-15-ephemeral-join-secret-for-wan-discovery.md` (ephemeral, rotating, window-scoped, scrypt-hardened rendezvous; open UX decision = code length, recommended 10 chars/50 bits — proposed, not yet implemented).

## Navigation Model

Two nested state machines, no router:

1. **Device/session phase** — `src/hooks/useDeviceMode.js` derives a `phase` from local state (`error` → `loading` → `mode-select` → `bootstrap`/`join` → `login` → `session`). `src/App.jsx`'s top-level `App()` switches on `device.phase` to render one of: `ModeSelectScreen`, `CampBootstrapScreen` (Host: create a new camp), `JoinByCodeScreen` (Client: enter the camp code shown on the Host, Stage 6 — replaced the old discovered-Host address picker, see the header note), `LoginScreen`, or the full `AppShell`. _Prior: the machine also had `pairing_pending` and `pairing_denied` phases rendering a ~~PairingPendingScreen~~. Both were gated on a stored join-host address, which nothing has written since the Stage 6c cutover removed the address picker, so neither phase was reachable; they were removed along with the three orphaned push channels (`shoresh:pairing-approved`, `shoresh:pairing-denied`, `shoresh:token-renewed`) that were their only exits. Pairing approval is now awaited inside `JoinByCodeScreen`'s own step machine via `joinAwaitPairingDecision`._
2. **In-app screen** — once in a session, `AppShell` (`src/App.jsx`) holds a `screen` string in `useState`, looked up in the `SCREENS` map and passed down through `Shell` → `Sidebar` (`src/components/layout/`). **Default landing screen is stage-aware** (ADR `docs/adr/2026-08-28-stage-aware-nav-landing.md`): `useState(() => campIsEmpty ? 'seed' : 'roots')` — a brand-new camp with no setup data lands on `SeedScreen` (`seed` key, the "Seed your camp" first-run screen, never reachable again once `campHasSetupData()` is true), every other camp lands on `RootsHomeScreen`. `campId` and an `onNavigate` (`navigate`) callback are threaded as props into every screen — no context, no router. The retired `'readiness'` key is **redirected to `'roots'`** at render (`resolvedScreen = screen === 'readiness' ? 'roots' : screen`) so stale deep-links/nav targets still resolve. The `navigate()` wrapper also carries drill-in focus targets (an elective set id, an event/special-day id) between screens, clearing each one the moment the director leaves the screen it targets.

**Sidebar structure** (`src/components/layout/navSections.js`, ADR `docs/adr/2026-08-28-stage-aware-nav-landing.md` Decision 3) — the "Seed → Germination → Sprouts → Roots → Plants" lifecycle IA (`docs/work/specs/2026-08-28-lifecycle-ia-program.md`): a fixed, chevron-less **Roots** row at top (`ROOTS_ITEM`, no fold state, always reachable); three collapsible stages (`NAV_SECTIONS`) — **Germination** (Age Divisions, Groups, Days, Time Blocks, Locations — the irreducible structure), **Sprouts** (Activities, Fixed Events, Recurring Events, Electives, Special Events — the program that grows from it), and **Plants** (Generated Schedule, Manual Build, Special Schedules, Elective Schedules — the schedules themselves; **pinned**, never collapsible, so the active-route highlight stays visible); and a gear-button **admin menu** (`ADMIN_MENU_ITEMS`: Camp, Re-import last year, Conflicts (badge), Trash) with `ADMIN_ONLY_MENU_ITEMS` (Devices, labeled "LAN & Devices") appended for `role === 'admin'`. ## Auth

Local, PIN-based, per-camp — not Supabase Auth (see architecture note above).

### Token types (device trust model)

Two token types are minted, verified, and enforced separately — see `electron/auth/localAuth.js` and `docs/adr/2026-07-25-device-trust-revocation.md`.

**Camp token (`type: 'camp'`)** — issued exclusively by the Host using its Ed25519 private key (`host_signing_key` table, generated once at `bootstrapCamp()`). Payload: `{type, userId, deviceId, campId, iat, exp, jti}`, base64url-encoded JSON, signature appended as `{payload}.{sig}`. 24h TTL (`TOKEN_TTL_MS`). The Host's Ed25519 public key is stored as `camps.signing_public_key` (hex-encoded DER/SPKI) and replicated to Clients via document sync — Clients can verify camp tokens but can never mint them (private key never leaves the Host). The libp2p auth gate (`electron/sync/automerge/authGate.js`, decision logic shared with the IPC path via `electron/auth/connectionAuth.js`) rejects any `local` token on the network path outright, the same behavior the retired WebSocket handler had.

**Local token (`type: 'local'`)** — issued by the Client itself using its device-scoped HMAC-SHA256 secret (`devices.device_secret_identifier`, a 32-byte hex value minted by the Host at device pairing approval). Used only for offline Client sessions (local IPC path). Never accepted on the network (libp2p) authentication path.

**Which token is issued** is re-derived from `host_signing_key`'s presence in the DB (`issueTokenForThisDevice`), never passed in by the caller — so callers can't get the routing wrong.

**Token verification** (`verifySessionToken(db, token)`): the `type` claim dispatches to Ed25519 verification (camp) or HMAC-SHA256 (local) only after parsing the payload — a tampered type claim doesn't reroute; it fails signature verification. `exp` is enforced (tokens past their TTL return null). Malformed tokens, unknown types, and missing DB rows all fail closed (return null).

### Device pairing and revocation

- **Stage 6 (2026-09-08) — join is now by camp code, not by picking a discovered address**: while an admin has an *Add a device* window open on the Host, the Host advertises a second, code-derived mDNS tag; the joining device (`JoinByCodeScreen.jsx`) enters that code, sends a `pairing_request` over the authenticated libp2p auth protocol, and the Host records it as a pending device — see the header note and `docs/adr/2026-09-08-libp2p-join-flow.md`. The camp's name is still never broadcast in the clear.
- Admin approves in `DeviceManagerScreen.jsx` — Host mints a `device_secret_identifier` and sets `devices.authorized_at`.
- Revocation: admin revokes via Device Manager → Host sets `devices.revoked_at`, `revoked_by_user_id`, `revocation_reason`; the revoked device's live libp2p connection is dropped (`authenticatedPeers` admission is cleared on disconnect and not re-granted).
- `devices` table fields: `id, name, last_seen_at, last_synced_at, last_synced_seq, authorized_at, revoked_at, revoked_by_user_id, revocation_reason, device_secret_identifier, libp2p_peer_id`. `libp2p_peer_id` (schema v57) is now live — it records the libp2p identity a paired device authenticated with (`electron/sync/automerge/peerIdentity.js`), not a dormant column.
- `authorize()` checks device revocation status on every privileged call — a revocation takes effect on the very next call from an already-connected device.
- The joining device shows its own waiting/denied steps inside `src/screens/JoinByCodeScreen.jsx`, which awaits the Host's decision over libp2p via `joinAwaitPairingDecision`. _Prior: these were `useDeviceMode.js` phases `pairing_pending` and `pairing_denied`, driven by push events; both were unreachable after the Stage 6c cutover and have been removed._

### Login paths

- `electron/auth/localAuth.js`: `attemptLogin(db, {name, pin, deviceId})` does the PIN check (`scryptSync` against `pin_hash`/`pin_salt`) + lockout tracking (`LOGIN_MAX_ATTEMPTS = 5`, `LOGIN_LOCKOUT_MS = 30s`). Issues the appropriate token via `issueTokenForThisDevice`.
- **Two login paths**, unified through `attemptLogin` so behavior can't drift:
  - Local IPC `login` handler (`electron/main.js`) — Host's own login, and a Client's offline fallback.
  - An unauthenticated `login` message over the libp2p auth protocol (`electron/sync/automerge/authGate.js`, replacing the retired WebSocket handler) — lets a genuinely fresh Client verify its PIN against the Host and receive a camp token before its first sync.
- `useDeviceMode` derives `phase: 'login'` when there's a camp/host but no token yet; `phase: 'session'` once a token exists.

### Role-Based Behavior — centralized authorization layer (Phase 2, 2026-07-25; network transport changed at Stage 6)

**Every** mutating IPC handler (`electron/main.js`) calls `authorize({db, token, action, resourceId})` (`electron/auth/authorize.js`) before proceeding — role is re-derived fresh from the `users` table on every single call, never trusted from the token payload or cached on an open connection. This replaced the pre-Phase-2 state (four scattered inline `role !== 'admin'` checks, only user-creation confirmed gated). **Since Stage 6c, mutations no longer travel over the network as individually-authorized operations** — a write is authorized once, locally, at the IPC boundary that originates it, then embedded in the Automerge document and replicated by merge; a peer receiving that merge enforces only connection-level admission (the libp2p auth handshake — see `transport.js`'s admission gate), not a second per-field `authorize()` re-derivation the way the old WebSocket `submit_op` handler did. This is a deliberate simplification of the sync path, not a coverage gap in the write path itself — see the Stage 6 ADRs for the reasoning.

- **`authorize()`** (`electron/auth/authorize.js`): verifies the token (`verifySessionToken`), re-queries `users`/`devices` by the decoded ids, resolves current role, looks it up against the permission matrix. Never throws (a db-layer failure returns `{allowed:false, reason:'db_error'}`, a malformed `action` is rejected for every role including admin). Returns `{allowed:true, userId, deviceId, role}` or `{allowed:false, reason}`.
- **Permission matrix** (`electron/auth/permissions.js`): `PERMISSIONS.admin = ['*']`; `PERMISSIONS.staff` is an explicit array — `<entity>.read`/`<entity>.write` for every entity in the exported `ENTITIES` list, plus `users.read`, `devices.read`, `conflicts.read`, `conflicts.resolve`. Staff does **not** get `<entity>.delete`, `<entity>.bulk_replace`, `camps.rename`, or `users.create` — admin-only.
- **Shared action-derivation** (`electron/auth/deriveWriteAction.js`): `deriveWriteAction({entity, field})` (3-way: `DELETE_FIELD` sentinel → `<entity>.delete`, `camps`+`name` → `camps.rename`, else → `<entity>.write`) and `deriveBulkReplaceAction(entity)` (→ `<entity>.bulk_replace`) are called by `electron/main.js`'s IPC handlers (`write`, `bulk-replace`) — the sole write-authorization call site now that the network path no longer re-derives it per operation (see above).
- **Deliberately left unwrapped** (no session token available at these call sites — pre-login/handshake-establishing, not an oversight): IPC `login`, `verify-session`, `choose-mode`, `discover-hosts`, `bootstrap-camp`, `get-camp`; the libp2p auth protocol's `authenticate`/`pairing_request`/`login` messages. `get-camp`'s query was narrowed to `SELECT id, name` (was `SELECT *`) during Phase 2 review — it had been unknowingly leaking `camps.signing_secret` (the HMAC key backing every session token) to any unauthenticated caller, which combined with staff-readable `listUsers`/`getDeviceId` would have let a compromised renderer script forge an admin token. Fixed before Phase 2 Task 2 was accepted; no renderer code depended on the dropped column.

| Feature | admin | staff |
|---|---|---|
| Camp setup, tiers, groups, time blocks, activities, anchors, day overrides, cohorts, templates — ordinary read/write | ✅ | ✅ (server-enforced via `<entity>.write`/`<entity>.read`, not just client-side button-hiding) |
| Delete any entity, bulk-replace (schedule regeneration/snapshot restore), rename camp | ✅ | ❌ (server-enforced, `<entity>.delete`/`<entity>.bulk_replace`/`camps.rename` absent from staff's matrix) |
| Create users (`createUser` IPC) | ✅ | ❌ (`users.create`, admin-only — routed through `authorize()`) |
| Schedule view/edit, conflict resolution | ✅ | ✅ |

`users.role` is a `CHECK (role IN ('admin', 'staff'))` column, re-queried fresh by `authorize()` on every privileged call — a role change (or a user/device deletion) takes effect on the very next IPC call using an already-issued token (`electron/auth/authorize.test.js`).

## First run and the sidebar's marks

**The pre-session screens share one backdrop.** `AuthWatermark` (the faint root
texture) runs on ModeSelect, CampBootstrap and JoinByCode; LoginScreen has its

wordmark in the condensed UI face.

**SeedScreen titles itself** — its `TITLES` entry is deliberately empty, because
the page puts "Seed your camp." in the display face as the moment it is meant to
be.

a change from the `·` rationale, which argued no row was ever wordless. The
guarantee that survives is the one that matters: **collapsing a section can
never hide a problem** — a collapsed header still shows `!`.

The one number left in the sidebar is the conflicts badge, which is an alert
count with an action behind it, not a description of how much of something
exists.

## Import and reconciliation: the director-facing contract

**A repeated question is asked once.** Identical decisions — same kind, entity
and reason sentence — group into one card that says "This came up N times".
Grouping is DISPLAY only: each decision keeps its own id and staged answer, so
the commit payload matches a director who clicked through every copy. Only
UNANSWERED cards group; an answered one keeps its own card because it carries
its own answer. Measured on one real file: 240 buttons to 32, 15.2 screens to
2.1. See `src/components/reconciliation/groupIdenticalDecisions.js`.

**The file control is a drop zone**, not a raw browser input, and it states the
six formats it accepts. The native `<input type=file>` is still the mechanism
and is positioned off-screen rather than hidden, so it stays focusable.

**The import preview's commit button is sticky.** That page reached 10,718px on
one real file.

**Where these live**, since three of them are shared and easy to re-break:
`src/components/reconciliation/groupIdenticalDecisions.js` (question grouping),
`src/screens/reconciliationTray.js` (the single exit's label and mode),
`S.btnRowDanger` vs `S.btnDanger` in `src/styles/shared.js`. Each carries the
measurement that motivated it in its own header comment, so the reasoning does
not have to be recovered from git.

**Destructive actions are quiet per row and loud once.** `S.btnRowDanger` is the
repeated row action; `S.btnDanger` stays for Delete Event, revoking a device and
every confirm dialog. 109 red Delete buttons down one table is wallpaper, not a
warning — the stakes live in DeleteRecordDialog, which computes the real
dependency count.

**Secondary actions do not sit where the primary one goes.** `S.btnUtility` is a
borderless text button for the file/bulk operations that accompany a setup
screen without being its point — Download Template, Import from Excel, Delete
All. They render in the **footer** (`SetupScreenShell`, and by hand in
`LocationsScreen`, which builds its own frame because it carries a Back
control), not top-right above the list, and Delete All is `btnUtility` in
`--warning` rather than the full `btnDanger` treatment it used to get there.
None of the three is hidden behind an overflow menu: a director who needs
Delete All needs to see that it exists.

**The week context bar is a page header, not a floating one.** `WeekContextBar`
renders in normal flow. It was the only `position: sticky` element inside the
scroll container, which meant it detached from the header and travelled down
over the table rows.

**The dev mock performs deletes and location merges for real.** `npm run dev`
(no Electron, so `src/localClient.mock.js` stands in for `window.shoresh`) is
the surface the app is demonstrated and design-reviewed on, and `deleteRecord`
and `mergeLocation` were stubs returning `{ error: 'no-record' }` — so Delete
and "Merge into …" were dead there while working in the packaged app. Both now
act on the mock's own store (a merge re-points the loser's activities at the
winner), and `previewDelete` returns the record's real name so a confirmation
does not read `Delete "this record"?`. Counts the mock genuinely cannot know —
slots cleared, routes touched — stay zero rather than being invented; those are
only verifiable under `electron:dev`. Pinned by
`src/localClient.mock.deleteMerge.test.js`.

## Reconciliation and the generated route

**There is one exit from reconciliation and it is never disabled.**
`src/screens/reconciliationTray.js` decides its label from how far the director
got: "Use this setup" when nothing is outstanding, "Apply N decisions" when some
are, "Use what Shoresh understood" when none have been answered. The screen
previously ended in two buttons where the navy PRIMARY stayed locked until every
item was resolved (79, on one real file) and the only reachable exit was the
secondary beside it — so a director who missed that had no way forward at all.
The two modes fold identical answers once everything is resolved, so collapsing
them costs no behaviour.

**The label carries the state, never a tooltip.** A tooltip explaining a
disabled control is help, and this app does not do help (owner, 2026-09-11: "if
it needs help, then we have UI wrong"). A screen that needs explaining is a
screen to redesign. There is no help affordance anywhere in `src/` and none
should be added.

**The counters name their unit.** The census tiles count ENTITIES; the progress
counter counts QUESTIONS. Read side by side without units, "1 Needs attention"
and "0 of 79 done" looked like a contradiction.

**The generated route opens to the schedule.** The concerns row (Placed /
Unfillable / Still needed) sits BELOW the grid. The engine has just done twenty
minutes of the director's work, and leading with counts of what is still wrong
reads as an audit of the result rather than the result.

## Ingest: what the extractor guarantees

The import path reads human spreadsheets — wrapped cells, merged headers, typos —
so its contract is about honesty rather than perfection.

- **Time blocks come out in clock order, not file order.** A real camp file does
  not list its periods chronologically, and `sort_order` is derived from the
  entity array's index, so `extractEntities` sorts before returning
  (`src/ingest/orderTimeBlocks.js`). Ordering a bare 12-hour label uses a stated
  camp-day rule — 1-6 afternoon, 7-12 morning/noon — because a running-clock
  reading cannot work on a file that is itself out of order. A leading zero means
  nothing: real camp files zero-pad 12-hour times.
- **`sort_order` is a dense sequence** for imported blocks. `gridGeometry`
  finds the next block by array position, so a non-dense column no longer
  silently disables span-merge (it did for hand-made blocks, which are written
  as minutes-from-midnight).
- **Change-overs are not periods.** A span of 10 minutes or less is passing time
  and is not imported as a schedulable block (`src/ingest/periodSpan.js`). The
  threshold came from the corpus: change-overs are 5-10 minutes and the shortest
  real period is 15.
- **One blank-line block can hold two periods, and they are split apart**
  (`src/ingest/splitPeriodBlocks.js`). A new period starts where the time column
  carries another time, once the period being accumulated has a complete label
  AND has seen data — both conditions matter, or the two halves of a wrapped
  label fragment, which is the bug blank-line blocks exist to fix.
- **A one-ended block is dropped when a range already covers its time**
  (`src/ingest/dropRedundantEndpoints.js`), and KEPT when no range does, because
  there it may be the only trace of a real period. campA imports as 11 periods,
  every one with a start and an end; it used to be 13 with four fragments, and
  before that 53.
- **Suspect names are flagged, never dropped.** `src/ingest/suspectRecords.js`
  marks activity names that begin with a joining word ("and Mitzvah") or with the
  period column's word ("Block Sports"), and the import preview shows them under
  "Worth a second look". Nothing is excluded from the import — "Art" trips a
  short-name heuristic and is a real activity, which is why the rules ask rather
  than decide.
- **`npm run ingest:sweep` runs on the committed fixtures** in
  `docs/work/specs/samples/` as well as on workbooks, and is the regression net
  for all of the above.
- **A workbook that is not schedule-shaped is refused, on every entry path.**
  `src/ingest/scheduleShape.js`'s `isScheduleShaped` requires positive evidence
  of a schedule — day-name columns, a day-named page title, or clock-time row
  labels — and is called both from `src/screens/ImportScreen.jsx` and, since
  T224, from `scripts/ingestCli.js`, which is what `scripts/mcp/tools.js`'s
  `ingest_preview`/`ingest_commit` run. Before T224 only the GUI enforced it, so
  the CLI and MCP would extract entities from any workbook at all: a campus-map
  template proposed 23 groups, 23 tiers and 21 "activities" (its legend keys —
  "building", "tent", "court") and reported success. **The shape gate is now
  PER-PAGE, not whole-file (T223).** `isSchedulePage`/`partitionSchedulePages`
  extract only the pages that individually pass the same positive-evidence
  test — a file mixing a real schedule tab with a non-schedule tab (a camper
  elective-selection sheet) now imports the schedule and DECLINES the other
  tab instead of extracting its column headers as groups/tiers. Declined tabs
  are surfaced, never dropped silently: the CLI/MCP result carries a
  `declinedPages` field (printed by `scripts/ingest.js`), and the UI's
  existing "Not recognised" box lists them by title. `isScheduleShaped` keeps
  its original whole-file contract (true if any page qualifies), so a file is
  never refused today that would have been accepted before this change — see
  `docs/adr/2026-09-18-schedule-shape-gate-per-page-granularity.md`. The
  per-entity template importers (Locations, Electives, Special Events) are
  non-schedule workbooks by design and deliberately never reach this check.

Known gap: the text-grid parser does not join period labels wrapped across two
lines, so `"9:50- Block" / "10:25  1"` is read as two fragments and that period
survives only as a bare "10:25". See
`docs/work/specs/2026-09-11-critique-fix-queue.md`.

## Database Tables

(SQLite, one file per device — `electron/db/schema.sql`, schema **v58** as of this writing)

- **camps** — `id, name, signing_public_key` (Ed25519 public key, hex-encoded DER/SPKI — replicated to all Clients so they can verify camp tokens). Exactly one row expected per device db (single-camp-per-db assumption used throughout, e.g. `SELECT ... FROM camps LIMIT 1`).
- **host_signing_key** — `id (always 1), public_key, private_key, created_at`. Host-only table; generated once at `bootstrapCamp()`. Never replicated. The private key never leaves the Host device.
- **source_aliases** — `id, camp_id, entity_type, cohort_id, source_label, entity_id, status ('active'|'superseded'), confirmed_by, confirmed_at, superseded_by` (schema v30, S1b). **Host-local, never synced** — deliberately absent from every sync registry (`projections.js`/`campScopedEntities.js`/`syncServer.js`), the same pattern as `host_signing_key`, so a tablet Client can neither forge nor diverge alias identity. Durable memory of "this imported label (e.g. 'Reds') means this live entity (the Red group)", used by the import's `confirmed_alias` matching tier so a repeat import auto-resolves instead of re-asking. Written by exactly one committer, `electron/ops/confirmAlias.js` (host-only, admin-gated `source_aliases.confirm`, supersede-on-reconfirm); the generic op-log path in `operations.appendOp` refuses `entity === 'source_aliases'`. Populated from the director's "Remember this" checkbox on the import's ambiguous-identity resolution card.
- **import_evidence** — `id, camp_id, entity_type ('activities'|'anchor_activities'|'groups'), entity_id, field, tag ('observed'|'inferred'|'unknown'), confidence ('high'|'low'), support (compact JSON), import_run_id, committed_at` (schema v31, B4; `'groups'` added 2026-09-13 for T114's division provenance — a group's `tier_id` is inferred from its NAME, so it needs the same auditability the activity rule fields have). **Host-local, never synced** — deliberately absent from every sync registry (`PROJECTIONS`/`DIRECT_CAMP_ENTITIES`/`full_sync`), the same trust model as `source_aliases` and `host_signing_key`. Durable record of *why* an ingested field holds the value it does (which observations/inferences supported it), backing the reconciliation "why" disclosure. Written only on the host-only import commit path. See ADR `docs/adr/2026-08-10-ingestion-evidence-persistence.md`.
- **users** — `id, camp_id, name, pin_hash, pin_salt, role('admin'|'staff')`. Unique on `(camp_id, name)`.
- **devices** — `id, name, last_seen_at, last_synced_at, last_synced_seq, pairing_status ('pending'|'authorized'), authorized_at, authorized_by_user_id, revoked_at, revoked_by_user_id, revocation_reason, device_secret_identifier, libp2p_peer_id`. `last_synced_seq` is the op-log watermark, now only meaningful for `oplog`-mode fallback (see header note) since the live sync path replicates the Automerge document rather than replaying individual ops. `pairing_status` defaults to `'pending'`; flips to `'authorized'` on admin approval. `device_secret_identifier` is the HMAC secret for local tokens, minted at pairing approval. `revoked_at`/`revoked_by_user_id`/`revocation_reason` are set at revocation; the live libp2p connection is dropped immediately (`transport.js`'s `revokePeer`). `authorize()` checks `authorized_at IS NOT NULL` on every privileged call — a device row without it is always denied. **`libp2p_peer_id`** (schema v57) is now live — records the libp2p identity a paired device authenticated with (`electron/sync/automerge/peerIdentity.js`), used for revocation and for dialing a device back with a pairing decision.
- **audit_events** — `id, camp_id, actor_user_id, device_id, action, outcome, reason, metadata (JSON), created_at`. Written by `electron/audit/auditLog.js`. Captured events include: `auth.login` (allow/deny with reason), `auth.authorize` (deny only — action + role + reason logged, no PIN/token material), device pairing and revocation events.`
- **operations** — the LOCAL HISTORY LEDGER (was the op-log; retired as a sync mechanism at Stage 6, kept as a record): `seq (autoincrement), id (unique), entity, entity_id, field, value, author_user_id, device_id, timestamp, parent_op_id, client_write_id`. **Retired as the sync mechanism at Stage 6c/6d, kept as a local history ledger** (`electron/automerge/historyLedger.js`) — sync now replicates the Automerge document, not these rows. `operations` still answers "what was deleted and by whom" (Trash), "what did this record hold before deletion" (Restore, since a CRDT document only holds current state), and backs ingest-undo; a merge received from another device now also appends rows here so those features keep working under the new engine, not only local writes. `client_write_id` remains a client-generated idempotency key. Rows now come from BOTH local writes (`appendOp`) and changes that arrive by document merge (`electron/automerge/historyLedger.js`) — without the latter a device could see a record it had no history for and could not restore.
- **conflicts** — durable record of every detected write conflict: `id, entity, entity_id, field, incoming_op, existing_op, existing_op_id, created_at, resolved_at`. Now populated by two independent producers into the same table/UI: the legacy op-log conflict path (a conflict resolved when any op has `parent_op_id = existing_op_id`), and, live by default, a CRDT reconciler (`electron/automerge/reconcile.js` + `conflictStore.js`, ADR `docs/adr/2026-09-08-crdt-conflict-reconciliation.md`) that unions concurrent edits to *different* fields automatically and writes a row only when two devices genuinely disagree on the *same* field — resolved by the director in the unchanged `ConflictsScreen`.
- **locks** — `entity, entity_id, field, holder_device_id, acquired_at` — field-level edit locks. **Unused by the live (Automerge) write path as of Stage 6** — every device now writes locally and converges by CRDT merge rather than negotiating a lock with a Host first (`electron/sync/localWriteClient.js`); a genuine same-field disagreement is now caught and surfaced after the fact via `conflicts`, not prevented beforehand. Retained for `oplog`-mode fallback.
- **groups**, **tiers**, **activities** — camp-scoped config entities, each `camp_id`-keyed.
- **template_slots** — `id, template_id, group_id, activity_id, day_id, time_block_id, anchor_id, is_anchor, is_span_head, flags`. `anchor_id`/`is_anchor` added in schema migration v17 (Sub-plan E Task 3) — were referenced by `BULK_REPLACE_ENTITIES`'s intended column set but physically missing from SQLite until this migration.
- **template_overlays — REMOVED (schema v53, ADR `docs/adr/2026-08-30-retire-overlay-stamp-subsystem.md`).** No live writer had existed since the day-overrides re-point (T108) retired its authoring path; `template_slots` (below) plus the events/electives/day_overrides family fully cover "special things on the schedule" now. `schedule_snapshots.overlays` was dropped in the same migration. Only registered `bulk_replace` entity today is `template_slots`. A rollback (`v53_down.js`) recreates the table (empty) for downgrade.
- **schedule_templates** — `id, camp_id, name, kind`. **A camp now holds up to TWO rows, one per schedule-building route** (`kind` = `'generated'` | `'manual'`), added by migration v23 (`CURRENT_SCHEMA_VERSION = 23`) together with `UNIQUE(camp_id, kind)` replacing v21's `UNIQUE(camp_id)`. Ids are derived, never minted: `deriveScheduleTemplateId(campId, kind)` (`electron/ops/scheduleTemplateId.js`) returns `schedule-template:${campId}` for the generated route — byte-identical to the pre-v23 one-argument form, which migration v21 still depends on — and `schedule-template:${campId}:manual` for the manual one. `kind` MUST be the first field written for a new row (write-ordering contract, documented at the `schedule_templates` entry in `electron/ops/projections.js`); written second, a manual row materialises as `'generated'`, collides, and is absorbed by `INSERT OR IGNORE`. Neither row is canonical — see `docs/adr/2026-07-28-plural-candidate-schedules-per-camp.md`. Legacy note: Local SQLite table (ported off Supabase in Sub-plan E Task 1/2). Was missing from `PROJECTIONS` (`electron/ops/projections.js`) until 2026-07-26 — ops were written to the op-log successfully but `applyProjection` silently no-op'd for every field, so the row never materialized. Fixed by adding the entry (commit `0ca1198`), same pattern as `groups`/`activities` etc. See Known Issues.
- **schedule_snapshots** — `id, template_id, name, is_auto, created_at, slots (TEXT/JSON), day_overrides_json (TEXT/JSON)`. **The `overlays` column was dropped at schema v53** alongside `template_overlays` itself (ADR `docs/adr/2026-08-30-retire-overlay-stamp-subsystem.md`); `slots` and `day_overrides_json` remain JSON-text columns — an explicitly scoped exception to this app's normal field-level op-log sync, not a pattern to reuse elsewhere (per the Sub-plan E design doc). Ported off Supabase in Sub-plan E Task 4. Gained a `PROJECTIONS` registry entry (`electron/ops/projections.js`) on 2026-07-24 — previously `ScheduleScreen.jsx`'s `writeFields()` calls to this entity silently never materialized the row (op-log write succeeded, but nothing projected it into the table); found and fixed while un-skipping the Sub-plan E Task 5 E2E regression test. **Second writer added 2026-09-02 (T117):** `electron/ops/materializeImportedVersion.js` writes one row named `"Imported schedule"` right after a schedule import commits (see "What's changed since"); `restoreSnapshot` (`src/screens/schedule/useSnapshots.js`) now drops any slot in a restored row whose referenced group/day/time-block/activity/anchor id no longer exists in the live catalog, reporting a skipped-cell count instead of writing a broken grid.
- **days_of_operation** — `id, camp_id, label, day_of_week, sort_order`. Default Monday-Friday rows are seeded on first camp mount by `src/utils/seedDays.js` (ported off Supabase 2026-07-24, previously `App.jsx`'s last live `supabase.from()` call site) — mirrors `ensureCohort.js`'s per-row completeness-check/repair pattern rather than a single "any row exists" flag, so a crash mid-seed self-repairs on the next mount instead of permanently under-seeding. SQLite can't attach a cross-column CHECK via `ALTER TABLE ADD COLUMN`, so the migration recreates the table (same shape as the v48–v50 `locations`/`camp_maps` rewrites). Held conflicts are explicitly out of scope (they never reach the commit write).
- **day_override_templates / day_override_template_slots — REMOVED (schema v46).** This detached override-template pair (superseded by the render-time `day_overrides` diff at v38) never had a writer after T108 retired `DayOverridesScreen`; both tables were empty and are now dropped. - **locations create path (T101 mitigation)** — not a new table, but note: deterministic location ids (`deriveLocationId`, T81/M4 ingest) now route through `resolveLocationCreateId`/`resolveLocationCandidateId` (`electron/ops/locationCreate.js` + `locationId.js`). |---|---|

## Edge Functions / API Routes

No Supabase Edge Functions or HTTP API routes — the local-first architecture has no server. All device-to-device communication is peer-to-peer over libp2p (`electron/sync/automerge/`): a dedicated auth protocol (`authGate.js`, message types `authenticate`, `pairing_request`, `login`, plus their `auth_ok`/`auth_failed`/`pairing_pending`/`pairing_approved`/`pairing_denied`/`login_ok`/`login_failed` responses) gates a separate doc-sync protocol (`transport.js`) that exchanges Automerge document bytes with any peer that authenticated on the connection. This replaced the custom WebSocket protocol (`electron/sync/syncServer.js`/`syncClient.js`, message types `authenticate`/`login`/`acquire_lock`/`submit_op`/`op_applied`/`op_conflict`/`full_sync`) at the Stage 6 cutover — see the header note.

**Machine-facing surface (not an HTTP API).** A headless **MCP server** (`scripts/mcp/server.js` + `tools.js`, launch `npm run mcp -- --db <path>`, stdio, read-only by default with an `--allow-write` gate; ADR `docs/adr/2026-08-21-mcp-ingestion-server.md`, plan `docs/work/plans/2026-09-01-machine-access.md`) exposes domain verbs over a camp's SQLite file with no Electron/IPC/auth: `ingest_preview`, `ingest_commit`, `list_entities`, `setup_summary`, `schedule_state` (**the validate verb** — re-runs the pure engine over stored placement, moving nothing. `findings` are what the app's Schedule screen shows for that same placement; `conflicts` are **not** — no screen renders them today, so this tool is presently the only place a caller sees them. As of T193 the `conflicts` array is genuinely computed (`src/engine/routeConflicts.js`, called from `src/engine/buildSchedule.js:879`): it re-derives combined location occupancy across regular activities, anchors, events and elective offerings, and reports `OUTER_RESOURCE_CONFLICT` wherever occupancy at one location/day/block exceeds that location's capacity — both across cohorts and within a single one. It is reporting-only and never moves a group or removes an offering. So an empty `conflicts` result now means "checked and clear" **for location-capacity contention, which is the only kind it evaluates** — it is not a general all-clear: a slot whose content carries no `location_id`, and a `location_id` that resolves to nothing in `locations`, are both treated as unconstrained and are not checked, deliberately matching `placeBlocked` in `buildSchedule.js`), `export_schedule` (the stable **`format_version: 1`** JSON schedule export), and two support/debugging tools added 2026-09-04 for the projection-failures ledger (see Database Tables): `check_projection_health` (read-only, always available — lists this device's unresolved projection failures) and `repair_projection_entity` (`--allow-write`-gated — re-derives one entity's row from its full op-log history). Neither of the latter two is director-facing. The same portable JSON export is available in the GUI (`src/utils/exportScheduleJson.js`'s `buildScheduleExport`, shared with the Excel export via `src/utils/scheduleCells.js` so the two can't drift; "Export data (JSON)" on the Schedule toolbar). The libp2p sync protocol is device-to-device plumbing, deliberately **not** exposed as a public API.

## Key Architectural Decisions

- **Ed25519 Host-only token minting**: camp tokens (used for network authentication) are signed with an Ed25519 private key that never leaves the Host. The public key (`camps.signing_public_key`, hex DER/SPKI) is distributed to Clients via full-sync so they can verify tokens but never mint them. Client offline sessions use per-device HMAC-SHA256 local tokens keyed to a `device_secret_identifier` minted by the Host at pairing. This replaced the original shared HMAC signing secret (`camps.signing_secret`) that was distributed to all devices — that earlier design meant any compromised device could forge tokens accepted by all others. See Auth section above for full details.
- **PIN sent over LAN for remote login**: a fresh Client verifies its PIN against the Host by sending it in the clear over the `login` message on the libp2p auth protocol (previously the WebSocket `login` message — see header note), rather than a hash — necessary because the Host must run its own `scryptSync` check. The libp2p connection itself is Noise-encrypted (unlike the retired plaintext `ws://`), so the PIN is no longer sent unencrypted on the wire, though it is still visible in-process to the receiving Host. Flagged for revisit if camps ever share network with untrusted devices.
- **Unified login path**: both local (offline fallback) and remote (online, incl. first-ever login) logins go through one `attemptLogin(db, ...)` function, so lockout/verification logic can't drift between the two call sites.
- **Stage 6 (2026-09-08): Automerge/libp2p is the live sync engine; the op-log is retired as a sync mechanism, kept as local history.** All mutations are still written through the same field-level `appendOp` shape locally, but replication between devices now happens by merging Automerge documents (one field = one document key — a Stage 6 fix, since the earlier one-container-per-record shape lost one side's fields 400/400 times when two devices concurrently created the same record), not by replaying `operations` rows over the wire. Genuine conflicts — two devices disagreeing on the *same* field — are still recorded in `conflicts` and require explicit human resolution in the unchanged `ConflictsScreen`; concurrent edits to *different* fields on the same record now merge automatically instead of contending. See the header note and ADRs `docs/adr/2026-09-08-flat-record-shape.md` / `docs/adr/2026-09-08-crdt-conflict-reconciliation.md`.
- **Single-camp-per-db assumption**: every `camps` lookup in the codebase does `SELECT ... FROM camps LIMIT 1` rather than filtering by an active-camp id — a device's SQLite file only ever holds one camp's data. This is a real constraint, not an oversight — changing it (e.g. to support multiple camps per device) would require auditing every one of these call sites.
- **Centralized authorization layer** (Phase 2, 2026-07-24/25, 4 tasks, ADR at `docs/adr/2026-07-24-centralized-authorization-layer.md`): replaced four scattered inline `role !== 'admin'` checks (and a completely unchecked WS layer) with one central `authorize()` primitive re-deriving role from the DB on every call, a named permission matrix, and shared action-derivation logic reused identically by the IPC and WS transports. See Role-Based Behavior above for the full shape. Explicitly out of scope for this phase (deferred): device pairing/revocation, token expiration/lifetime, any change to the shared-camp-signing-secret token-minting model, raw PIN transmission changes, full audit-event-stream infrastructure (a single `console.warn` on a denied `authorize()` call is the only logging added).
- **Connectivity observability at the discovery/dial/auth seam** (T212, ADR `docs/adr/2026-09-18-connectivity-observability-event-vocabulary.md`): `electron/sync/automerge/mutualAuth.js` emits a small, closed set of structured JSON log lines (`electron/sync/automerge/connectivityEvents.js`) at every outcome of discovering, dialing, and mutually authenticating a peer — `PEER_DISCOVERED`, `TRUST_CHECK_REJECTED`, `DIAL_FAILED`, `ATTEMPT_STALLED`, `AUTH_REJECTED`, `AUTH_ERROR`, `AUTH_OK`, and `NO_TOKEN` — so a pairing failure can be read from logs as discovery-layer, dial-layer, or auth-layer instead of one ad-hoc `console.error` string. Peer ids are logged in full; multiaddrs are classified (`loopback`/`private`/`cgnat`/`public` + a count) rather than logged literally unless an operator sets `SHORESH_CONNECTIVITY_LOG_ADDRS=1` for a manual test run; error objects are reduced to a closed `errorClass` enum before reaching a log line, never the raw message. Every attempt-scoped event carries an `attemptId` so overlapping attempts for the same peer (T230, `docs/work/tickets/T230-stalled-dial-is-never-cancelled.md`: the watchdog aborts a stalled dial/authenticate via `AbortSignal` and clears an attempt-ownership token so a stale settlement cannot mutate a newer attempt's bookkeeping) can be told apart in the data, and repeated `PEER_DISCOVERED` announces for the same peer are folded into one line per 30s window with a `repeatCount`, rather than one line per mDNS re-announce. **What this instrumentation cannot yet tell an operator**, because mDNS is link-local multicast and cannot cross a router or NAT: whether two devices on different networks failed to connect because of NAT type is not answerable from this data today — an absence of `PEER_DISCOVERED` between two WAN devices is expected regardless of NAT type until a WAN-capable discovery path (the still-parked rendezvous adapter, T211) exists to produce a `PEER_DISCOVERED` at all. `RENDEZVOUS_UNAVAILABLE` is defined and unit-tested but emitted by no running code — reserved vocabulary for T211. No file under `electron/sync/automerge/rendezvous*.js` is imported by any running path, and `transport.js` is untouched by this work.
- **`bulk_replace` op primitive**: a `{entity, scope_id, rows}`-shaped op that deletes all current rows in scope and inserts a new set, atomically, recorded in the op-log like any other op. Built in Sub-plan A Task 3 (`appendBulkReplaceOp`/`applyBulkReplaceProjection`/`validateBulkReplaceRows` in `electron/ops/operations.js`), extended with a renderer-facing IPC channel and a second (`template_overlays`) registry entry in Sub-plan E Task 3. **`template_overlays` was retired at schema v53** (ADR `docs/adr/2026-08-30-retire-overlay-stamp-subsystem.md`), so `BULK_REPLACE_ENTITIES` (`electron/ops/operations.js`) now registers only `template_slots`. Used by `ScheduleScreen.jsx` for schedule regeneration and snapshot restore — the only consumer. As of Phase 2, admin-only via `<entity>.bulk_replace` on both the IPC and WS submission paths.
  - **FIXED 2026-07-24** (previously CRITICAL, found by Sub-plan E Task 5's end-to-end verification, `electron/sync/scheduleE2E.sync.test.js`, originally left as an honest `it.fails` regression test — now un-skipped and genuinely green): `applyRemoteOp` in `electron/sync/syncClient.js` inserted a received op without persisting its Host-assigned `seq` (`electron/db/schema.sql`: `seq INTEGER PRIMARY KEY AUTOINCREMENT`) — each device's local `operations.seq` was that device's own independent counter, not the Host's canonical one. `latestScopeOpSeq`/`detectBulkReplaceConflict` (`electron/ops/operations.js`) compared a client's locally-numbered `based_on_seq` directly against the Host's own seq counter as if they were the same numbering space, so the SECOND `bulk_replace` to the same scope from the same client (build a schedule, then click Regenerate) spuriously conflicted in essentially all real usage. **Fix** (full Architect + Maker + review cycle, ADR at `docs/adr/2026-07-24-bulk-replace-seq-fix.md`): added a nullable `operations.host_seq` column (schema v18); `applyRemoteOp` now persists the Host's real `op.seq` into it on insert; `latestScopeOpSeq` compares `MAX(COALESCE(host_seq, seq))` instead of raw `seq`, so Host-authored rows (host_seq always NULL, own seq already canonical) and Client-replicated rows (host_seq populated) share one numbering space. `isValidRemoteOp` now requires `op.seq` be a non-negative integer (fail-closed). Disclosed, accepted residual limitation: operations rows from before this migration have `host_seq = NULL`; if Client-authored, scope-seq comparison falls back to that row's own (possibly wrong) local seq until superseded — at most one spurious conflict per scope post-upgrade, then self-healing (mathematically bounded, verified by Red Hat review), no backfill migration needed.

- **Host-local aliases, never synced** (S1b, schema v30, ADR `docs/adr/2026-08-09-s1b-host-local-aliases.md`): confirmed source→entity aliases live in a host-local `source_aliases` table that is deliberately absent from every replication registry — the same trust model as `host_signing_key`. Chosen over a synced/replicated alias design (two earlier ADRs, now superseded) because it dissolves an entire class of cross-device divergence/replay complexity: there is exactly one writer (`confirmAlias.js`, host-only + admin-gated), so alias identity can't be forged over the wire or diverge between devices. Trade-off accepted: aliases are per-host, not shared to Clients — fine because import is already host-only.
- **Re-import provenance protection (Policy A), one shared channel** (S2a/S2b + 2026-08-09 ingest fixes): a director's hand-edit is stamped `operations.source = 'human'`; an import writes `'import'`. On re-import, a field whose latest op is `'human'` is not silently overwritten — it holds a stale conflict for review (`isProtected = !!latestOp && latestOp.source !== 'import'`). Review-time hand-edits (a unit assignment/clear, a group field, an activity rule) reach this via ONE generic side-channel: the renderer sends `humanEditedFields: { <entity>: { <name>: [fields] } }` through the host-trusted `shoresh:ingest-commit` IPC path only; `buildPlan` attaches it per-item as `_humanFields`; `commitCreate`/`commitUpdate` stamp those fields `'human'`. This channel is unreachable from the WS `submit_op` path, so it adds no forgery surface. All three provenance gaps (units/tiers, groups, activity rules) are closed by this one mechanism.
- **Fixed events route to the schedule, not the activity catalog** (2026-08-09, ADR `docs/adr/2026-08-09-ingest-fixed-event-routing-and-reviewable-units.md`): a name pinned across the grid (Lunch, Mifkad, Sign-In) was being written BOTH as a catalog `activities` row and as `anchor_activities`. It now defaults OUT of the catalog. Critically, this is a **visible, reversible review decision**, not a silent engine drop — `inferFixedEvents` returns `dualUseNames` only as a SEED for the import review's tick-defaults (pin-only rows default unticked with a note + one-click override; genuinely dual-use names default kept, flagged). `buildPlan`/`commitPlan` are unchanged and golden-ops stay byte-identical. This deliberately avoids letting the fixed-event detector's intentional over-inclusion silently delete a legitimate catalog activity.

**The document carries provenance and authorship; the op-log becomes a local history ledger (2026-09-08/09).** Completing the
Stage 6 cutover. `applyWrite` used to carry field VALUES only, which broke two things a director relies on.

- **Hand edits survive a re-import made on another device.** ADR
  `docs/adr/2026-09-09-field-provenance-in-the-document.md`. `ingest.js` protects a hand edit by asking whether a field's latest
  write was human, reading `source` from `operations` — and a field that arrived by document merge has no op row on the receiving
  device. At `ingest.js:452` it was worse than "unknown": it evaluated to `'import'`, positively recording the director's own
  correction as having come from the spreadsheet. The document now carries a SPARSE `field_provenance` collection (a key only for
  fields a human owns, cleared when an import takes the field back), and `electron/ops/fieldProvenance.js`'s `isHumanOwned` is the
  single answer — with the document authoritative in BOTH directions for a field it holds, so a stale ledger row cannot freeze a
  field against re-import. Integration scenario 29.
- **"Who changed that?" has an answer on the other device.** A `field_author` collection carries who last set each field, plus a
  deliberate tombstone for who DELETED a record — the one marker that must OUTLIVE the record it describes, because every other
  trace of a deleted record is gone from the document by design and Trash's "deleted by" column reads exactly that. Kept a separate
  collection from `field_provenance` because provenance is deliberately sparse and authorship is not. Integration scenario 30.
- **`operations` stays, as a LOCAL HISTORY LEDGER.** The op-log is retired as a SYNC mechanism only. Trash, Restore and ingest undo
  answer from op rows, and a CRDT document holds CURRENT state — a deleted record is simply absent from it, so the history is the
  only place its old values still exist. `electron/automerge/historyLedger.js` writes rows for changes that arrive by merge
  (deliberately NOT via `appendOp`, which would project again and echo the change back out as a local one). Integration scenario 18,
  deferred through the port and now green.
- **Both new collections live in the frozen genesis, never created on first write** — a lazily created collection is a concurrent
  create of the same map key from two actors, which Automerge resolves by keeping one side and discarding the other into
  `A.getConflicts`, which nothing reads. Fourth and fifth `GENESIS_B64` regenerations; existing `.automerge` files are discarded
  (pre-production, accepted).
- **A director can now actually resolve a CRDT conflict.** Its competing values come from the document and only the winning side
  gets a ledger row, so `resolveConflict`'s `chosen_op_id` lookup against `operations` used to refuse the losing side — the only
  choice worth offering — with "chosen operation not found".

Their per-entity sub-schedule editors (`EventGridEditor`/`EventCell`, `SpecialDayGridEditor`/`SpecialDayCell`) carried over unchanged as the merged screen's row-detail views; the Plants-side build surface (`SpecialSchedulesScreen`, `schedule:special`) is untouched.
- **The entire spatial / facility-map layer** (`src/screens/DayMapScreen.jsx`, the Locations Map tab, the drag-to-place Canvas, the Tile-World simulation, `src/data/deriveOccupancy.js`, and all associated map helpers) — **deleted in PR #201 (commit `335e311`)**, a `chore:` removal with no ADR. - **`@supabase/supabase-js` dependency, `src/supabase.js`, `supabase/migrations/`** (removed/moved 2026-07-24) — the entire pre-rebuild Supabase backend. Moved to `legacy/supabase/` for historical reference; no longer a project dependency; reintroduction under `src/`/`electron/` is blocked by an ESLint rule. This closes out the renderer-migration-plus-hardening project that spanned Sub-plans A-E plus this final Phase 1 cleanup — every screen, the last bootstrap call site (`seedDays`), and the legacy files themselves are now off Supabase, and the sync layer's one known CRITICAL defect (`bulk_replace` cross-device seq bug) is fixed.
