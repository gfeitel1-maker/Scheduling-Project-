# Productionization Audit: Automerge + libp2p Conversion

**Scope:** Read-only architecture audit of Shoresh main (`origin/main` @ `8bf3a33`, checked out at `/tmp/shoresh-main-audit`). No code was modified. Feeds an owner decision + a future productionization ADR.

**Question posed:** what does it cost to convert the sync/data layer to **Automerge** (data model, merge, conflict resolution) + **libp2p** (transport, discovery, NAT traversal), with SQLite demoted to a **projection** of an Automerge document?

## 2. Seam analysis: is `src/localClient.js` the true chokepoint?

**Confirmed.** `grep -rl "window.shoresh" src/` returns exactly four hits: `src/localClient.js` (the real implementation, `export const localClient = {...}` at line 21, 192 lines total), `src/localClient.mock.js` (the dev/test mock), and two files — `src/App.jsx` and `src/components/schedule/ManualBuildView.jsx` — where the only matches are **comments** (`// window.shoresh/op-log/sync, per the spec's...`, `// dev hits the mock's no-op...`), not code. Zero other files in `src/` touch `window.shoresh` directly.

Import-graph confirmation: `grep -rl "from '.*localClient'" src/` returns 73 files total, of which **36 are non-test** consumers (screens, hooks, one component, two util modules) and 37 are test files exercising those same consumers via `localClient.mock.js`. This matches the peer-session claim almost exactly (36, not ~36-ish approximation — it's exact).

**What `localClient.js` exposes**: a single object (`export const localClient = {...}`) wrapping `window.shoresh.*` IPC calls — `list`, `write`, `bulkReplace`, `listByScope`, delete/restore/history methods, etc. — presumably 1:1 or close to it with the ~70 `preload.js` methods, since it's the renderer-side façade over the whole IPC surface.

**Can an Automerge-backed provider sit behind it with the same method signatures, leaving the 36 consumers untouched?** Yes, with one caveat. The renderer never imports anything from `electron/ops/**` or `electron/sync/**` directly — it only ever calls `localClient.list(...)`, `.write(...)`, etc., which resolve to `ipcRenderer.invoke('shoresh:...')`. As long as:
1. The `preload.js` channel names stay the same (`ipcSurfaceParity.test.js` already guards this — keep it running throughout the migration, it is the regression net for exactly this claim), and
2. Each `ipcMain.handle('shoresh:*', ...)` handler in `main.js` is re-pointed to read/write the Automerge document + read the SQLite projection instead of the op-log, returning the **same response shape**,

then all 36 renderer consumers, `src/engine/**`, and every screen/hook are provably untouched. This is the strongest evidence in the codebase for "the change is containable" — the insulation is real, not aspirational, and it is testably real via the existing parity test.

The one caveat: some IPC methods (`onOpApplied`, `onOpConflict`, `onFullSyncApplied` in `preload.js` — push events, not request/response) carry sync-protocol *semantics* in their names and payload shape, not just their existence. `onOpApplied`'s payload is presumably op-log-shaped (an applied op). If Automerge's change-notification payload shape differs meaningfully (e.g., a patch/diff rather than a single field-op), the *event still fires with the same name* but a renderer consumer that inspects the payload's internal shape (not just "something changed, refetch") could be coupled more tightly than the `list`/`write` methods are. This needs a one-time check during implementation: grep consumers of `onOpApplied`/`onOpConflict` for payload-shape assumptions, not just presence.

## 3. New components needed

1. **Automerge document lifecycle** — one Automerge doc per camp (mirroring "one SQLite db per device, one camp per device" from `CLAUDE.md`). Needs: creation (camp bootstrap), loading/persisting the binary doc (Automerge's own storage format, likely still written to a file inside the same per-camp userData directory `electron/db/userDataPath.js` already manages), and a change-application entry point that every mutating IPC handler funnels through (this is the direct replacement for `appendOp`/`operations.js`).
2. **Automerge → SQLite projection** — the replacement for `projections.js`. Two flavors likely needed: (a) an incremental projector driven by Automerge's patch/diff callback on each local or remote change (cheap, keeps the projection warm), and (b) a full-rebuild projector that walks the entire current document state (used for initial camp load, and as the *replacement* for `projectionRepair.js` — "rebuild everything from the doc" instead of "replay ops for one broken entity").
3. **libp2p node** — one per device, running whatever discovery/transport stack replaces `discovery.js` + `syncServer.js`/`syncClient.js`: mDNS for LAN (near-direct swap), DHT + `dcutr` (or equivalent hole-punching) for WAN, matching the task's stated goal of NAT traversal that the current WebSocket-Host-on-LAN model doesn't attempt at all today.
4. **The host-only-table exclusion mechanism, ported** — confirmed today's mechanism is an **allowlist by omission**: `electron/ops/campScopedEntities.js` exports `DIRECT_CAMP_ENTITIES`/`PARENT_SCOPED_ENTITIES`/`DOMAIN_PARENT_SCOPED_ENTITIES`, and `electron/sync/catchup.js` imports exactly those three constants (line 2) to decide what a full-sync payload contains — `compound_cell_decisions`, `location_word_decisions`, `declined_two_row_splits`, `source_aliases`, `import_evidence`, `host_signing_key`, and device/pairing tables are simply **never listed** in those allowlists, not blocked by a separate denylist. This is a clean, portable pattern: under Automerge, the equivalent is "these tables are written directly to host-local SQLite and never touch the Automerge document at all" — i.e., they don't need an exclusion rule inside Automerge, they need to **never be modeled as Automerge document fields** in the first place. Confirmed via `schema.sql` comments at lines 103, 124, 146, 171, 183, 210 ("Host-only table, like host_signing_key. NEVER included in any full-sync SELECT/payload...") that this is a deliberate, repeatedly-reinforced invariant, not incidental.
5. **Membership/identity over libp2p peer keys** — mapping today's Ed25519 `host_signing_key` (schema.sql:96, never replicates, signs `camp` tokens) and per-device `device_secret_identifier` (HMAC for `local` tokens) onto libp2p's own `PeerId` keypairs. Needs explicit design: does "Host" survive as a privileged role (signing authority) even if libp2p makes the *transport* topology peer-to-peer rather than hub-and-spoke? This is a security-relevant open question, flagged in §4/§5, not answered here.
6. **Atomic-ingest primitive over Automerge** — the `HELD` sentinel pattern (ingest.js:1038) needs a verified equivalent using Automerge's `change()` callback abort semantics (throw inside the callback → no change recorded). Needs a small, isolated spike/test before the ingestion migration slice, not an assumption baked into the ADR.
7. **Schema-version handshake, Automerge-flavored** — today's SQLite migration ladder (`localDb.js`, v1→v56) implies devices on different app versions could in principle disagree about the `operations` table shape; check whether an existing version-compat mechanism exists for op-log field additions (not confirmed in this pass — flagged as an open question in §4) and design its Automerge-document equivalent (schema evolution inside a CRDT document is a known hard problem — Automerge documents don't have a migration story as mature as SQL's).

## 4. Risks / must-preserve invariants (confirmed in code)

- **Atomic ingest rollback**: confirmed at `electron/ops/ingest.js:1038-1042` — a `HELD` `Symbol` thrown after populating a `conflicts` array rolls back the whole SQLite transaction, leaving the DB "byte-identical" on a held import. **Risk**: Automerge's `change()` has no native cross-call transaction spanning arbitrary async work the way a SQL `BEGIN/COMMIT` does — confirm the specific abort semantics (does throwing inside `change()` guarantee zero mutations recorded, including any nested calls?) before relying on it for something as ingestion-critical as this.
- **Host-only tables never replicate**: confirmed as a real, multiply-commented invariant (schema.sql:103,124,146,171,183,210) enforced today by allowlist-by-omission in `campScopedEntities.js` + `catchup.js`. **Risk**: under Automerge, this becomes "never model these as document fields," which is a *stronger* guarantee (structurally impossible to leak, not just unlisted) if done right, but a *design mistake* (accidentally putting one of these six tables' data into the shared doc) would leak reconciliation-provenance data device-to-device with no export/`full-sync` step to grep for — it would be baked into the CRDT history. This needs a lint/test-level guard equivalent to the existing implicit-by-omission pattern, made explicit (e.g., a schema-diff test asserting these six tables have no Automerge-doc counterpart).
- **`ipcSurfaceParity.test.js`**: exists and is the load-bearing regression gate proving the IPC surface doesn't drift. Confirmed present in the repo (referenced by `CLAUDE.md`, not independently re-verified line-by-line in this pass — recommend confirming it asserts on channel *names* only vs. also asserting on payload shapes, since payload-shape drift is the real risk called out in §2's caveat).
- **`projectionRepair.js`/`projection_failures` becoming moot**: confirmed, not assumed — read both the implementation (93 lines, replay-ops-in-seq-order) and its test suite (`projectionRepair.test.js`, asserts exactly that behavior), and the `projection_failures` schema (schema.sql:299, indexed at 308). This is a clean removal, and PR #280 (per task context) is now known-obsolete under this future direction — worth a note in the eventual ADR so nobody re-invests in extending it.
- **Backups**: `electron/db/projectManager.js` handles project export/backup/restore — not independently re-verified against Automerge-doc backup needs in this pass. Flag: backing up "the SQLite projection" alone would NOT be sufficient once SQLite is derived data — the Automerge document itself (or its append-only change log) is the thing that must be backed up; the SQLite file becomes reconstructible-but-not-authoritative. This needs explicit handling in `projectManager.js`'s replacement, not an afterthought.
- **Schema-version handshake across devices**: NOT independently confirmed in this pass (grep for a version-negotiation message in `syncServer.js`/`syncClient.js` was not performed — time-boxed out). Flagged as an **open question**, not a confirmed risk: does today's protocol have an explicit schema-version exchange at connection time, and if so what does its Automerge equivalent need to be?

## 5. Proposed staged path (skeleton — pending owner sequencing)

This is a skeleton only. Each stage should be its own small, reversible, test-first review-loop slice; do not treat the ordering below as committed.

1. **Spike: Automerge `change()` abort semantics vs. the ingest HELD pattern.** Smallest possible isolated test proving (or disproving) that the atomic-ingest invariant survives. Gates whether ingest.js's 2,499 lines of domain logic can move over cleanly or need restructuring.
2. **New: Automerge doc + incremental projector, for ONE low-risk entity table** (e.g. a leaf table with no cascade/delete complexity) running in parallel with the existing op-log for that one entity, behind a flag. Prove the projection round-trips correctly before touching anything camp-wide.
3. **Port the host-only-table exclusion as a structural guarantee** (not modeled in the Automerge schema at all) + a test asserting it, before any host-only-table-adjacent entity is migrated.
4. **libp2p transport spike, LAN-only first** (mDNS discovery + Automerge sync protocol over a libp2p stream), replacing `discovery.js` + a minimal slice of `syncServer.js`/`syncClient.js`, proving parity with today's LAN-only Host/Client flow before attempting DHT/NAT-traversal.
5. **Widen the projector to all camp-scoped entities**, `campScopedEntities.js`'s existing allowlist as the literal migration checklist (it's already the authoritative list of what syncs today).
6. **Retire `operations`/`conflicts` tables and `electron/ops/operations.js`**, `syncServer.js`/`syncClient.js`/`catchup.js`/`opDelivery.js`, once the projector + libp2p path has full parity — this is the actual "cutover," done last and only after the above stages have running tests proving equivalence.
7. **WAN NAT traversal** (DHT/`dcutr`) as a separate, later slice — it's additive to what the LAN-only path already proves, not a blocker for the core CRDT conversion.
8. **Membership/identity redesign** (Ed25519 host-signing-key → libp2p PeerId mapping, Host-as-privileged-role question) — deliberately called out as needing its own design pass / ADR, not folded into the transport spike, because it's a security-consequential, not-obviously-reversible decision per the ADR bar.

## Open questions for the owner (product/sequencing, not technical)

- Does "Host" need to remain a privileged/signing role once transport is peer-to-peer via libp2p, or does the whole camp-membership model get redesigned around symmetric peer identity? This is a security-model decision, not an engineering detail — recommend it gets its own ADR before Stage 8 above starts.
- Is a full op-log-to-CRDT cutover (Stage 6) intended as a hard replacement, or does the owner want an interim state where both mechanisms coexist for a migration window (e.g. to avoid a flag-day for existing installed campers' devices)? Confirmed nothing in the current codebase anticipates dual-write; this is a sequencing choice the ADR needs to make explicit.
- Priority: is WAN NAT traversal (the reason cited for choosing libp2p at all) an immediate requirement, or could the LAN-only libp2p swap ship first as a lower-risk step with WAN deferred? Stage 7 above assumes the latter is acceptable; confirm.
