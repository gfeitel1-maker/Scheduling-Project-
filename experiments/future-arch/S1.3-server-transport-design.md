# S1.3 — WebSocket server-side transport design

Per `docs/adr/2026-08-17-shared-project-multi-transport-sync.md`, stage S1 ("Transport seam").
S1.2 shipped the client half (`webSocketClientTransport.js`); this slice adds the server half.
Additive only — nothing in the running app imports it yet.

## Decision: Model A — a listener, not a Transport

`createWebSocketServerListener(opts)` is **not** a `Transport` and is never passed to
`assertIsTransport`. It exposes `id`, `start()`, `stop()`, `onConnection(handler)`,
`onDisconnection(handler)`. Each accepted socket is handed out as its own conforming
`Transport` ("peer channel") via the `onConnection` callback: `(peerChannel, peerId) => {}`.

**Why not make the listener itself a Transport (Model B, rejected):** the contract in
`transport.js` describes one bidirectional channel to *one* counterpart — `send(message)` means
"send to my one peer," `onMessage(handler)` means "deliver from my one peer." A listening server
has zero-to-many simultaneous counterparts at once. Overloading `send()` to mean "broadcast to
everyone currently connected" would silently redefine what `send()` means depending on which side
of the seam created the transport, and there would be no way to reply to only one peer without a
second, non-contractual API bolted on. Model A keeps the seam's meaning identical on both ends:
a `Transport` is always exactly one channel to exactly one counterpart. The listener's only job is
accept + hand out; everything else — who to broadcast to, how to track peers — stays one layer up,
exactly where it already lives today (see evidence below).

## Verified syncServer.js evidence for this shape (cited, not assumed)

Read `electron/sync/syncServer.js` before designing, to check what the *existing* server already
does with per-connection state, rather than inventing a shape the app doesn't need:

- **No separate peer registry.** `wss.clients` (the `ws` library's own `Set` of live sockets) *is*
  the registry. There is no parallel `Map<peerId, …>` maintained by application code. Confirms
  that Model A's "hand out a channel per connection, let the caller track what it needs" fits how
  this codebase already thinks about connections — it doesn't pre-suppose a peerId-keyed structure
  the app doesn't otherwise want.

- **`deviceId` is set late, well after the socket exists**, in `handleAuthenticate`:
  `electron/sync/syncServer.js:454` — `ws.deviceId = verified.deviceId`. The socket is created and
  already accepting messages before authentication completes (`electron/sync/syncServer.js:364`,
  `handleAuthenticate(db, ws, msg)`, itself dispatched from the message handler around
  `electron/sync/syncServer.js:1088`). This is exactly why S1.3's `peerId` must be assigned by the
  *listener* at connect time and must be an opaque counter, never `deviceId` and never derived from
  remote address: at the moment a channel is handed to `onConnection`, no device identity exists
  yet to key on.

- **Broadcast = iterate `wss.clients` and filter, not a dedicated broadcast primitive on the
  socket/server object.** `electron/sync/syncServer.js:692-702` (`handleSubmitOp`'s broadcast) and
  the standalone `broadcastOps(wss, ops)` helper at `electron/sync/syncServer.js:820-829` both do:
  ```js
  for (const client of wss.clients) {
    if (client.deviceId) {
      try {
        if (client.readyState === client.OPEN) send(client, { type: 'op_applied', op })
      } catch {
        // never let one dead client stop the broadcast to others
      }
    }
  }
  ```
  Same shape again at `electron/sync/syncServer.js:794-802`. This is caller-side iteration over a
  live collection, filtering on state the caller cares about (`client.deviceId` truthy — i.e.
  "authenticated" — and `readyState === OPEN`), with a per-client try/catch so one dead peer never
  aborts the broadcast to the rest. S1.3's design statement "broadcast is NOT a listener method —
  it's caller logic" is not a guess; it is the existing, working pattern, restated for the new
  per-peer-channel shape (`for (const { ch } of channels) await ch.send(msg)` instead of
  `for (const client of wss.clients) send(client, msg)`).

- **Targeted send = replying on the same `ws`.** Every non-broadcast reply in `syncServer.js`
  (e.g. the `op_rejected` reply at `electron/sync/syncServer.js:681-688`) just calls
  `send(ws, {...})` on the one socket that sent the request — there is no separate "send to peer
  N" addressing scheme. This maps directly onto "call `.send()` on that one peerChannel" in the new
  seam; no new addressing concept had to be invented.

## Test approach

`webSocketServerListener.contract.test.js` uses the **real S1.2 client transport**
(`createWebSocketClientTransport`) as the connecting peer(s), not a bare `ws` client — so the test
exercises a genuine client-transport ↔ server-listener round trip over a real loopback socket, the
same way two real Shoresh devices would talk once S1.5 wires this in. Port is ephemeral
(`getFreePort()`, same helper pattern as `webSocketClientTransport.contract.test.js`) per the
repo's fixed-port flake history.

Coverage: start/stop; `onConnection` firing with a peerChannel that itself passes
`assertIsTransport` plus an opaque peerId; `'connected'`/`'disconnected'` status on handout and on
client disconnect; `onDisconnection` firing with that peerId; message delivery both directions;
multi-peer (two client transports get two distinct peerIds; a caller-iterated broadcast reaches
both; a targeted `.send()` on one channel reaches only that client); FIFO order per channel;
unsubscribe; `send()` after disconnect rejecting.

One non-obvious bug this test surfaced and fixed: Node's underlying `server.close()` (backing the
`ws` `WebSocketServer`) stops accepting new connections but does **not** proactively close sockets
already open — its callback only fires once every existing connection has ended on its own. A test
that calls `listener.stop()` while a peer is still connected would hang forever. The listener now
tracks its own live sockets and calls `.close()` on each before closing the underlying server, so
`stop()` always resolves and every peer channel reliably observes `'disconnected'`.

## Explicit non-rewiring note

`syncServer.js` is **not** touched or rewired onto this listener in this slice. `git status
--porcelain electron/sync/syncServer.js electron/sync/syncClient.js electron/main.js` is empty.
Migrating the running server onto `webSocketServerListener.js` is **S1.5**, a separate slice that
must go through the full Governor → Maker → review loop (behavior-preserving migration, same
discipline as S1.2's planned client-side migration) — not bundled into this additive, currently-dead
seam.
