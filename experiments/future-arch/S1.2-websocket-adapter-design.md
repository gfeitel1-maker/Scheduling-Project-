# S1.2 — WebSocket client Transport: design note

Status: additive, built, green. `syncClient.js` is **not** rewired onto this transport —
that migration is S1.4 and must go through the full Architect → Maker → Verifier loop,
not be smuggled into this slice.

Parent ADR: `docs/adr/2026-08-17-shared-project-multi-transport-sync.md` (S1 = "transport seam").
Contract: `electron/sync/transport/transport.js`. Reference impl: `electron/sync/transport/inMemoryTransport.js`.

## Seam evidence from the real code

Read to ground the design, not guessed:

- `electron/sync/syncClient.js:599` — `ws = new WebSocket(serverUrl)`, the one construction site.
- `electron/sync/syncClient.js:601-617` — `ws.on('open', ...)`: sends `authenticate` or
  `pairing_request` depending on whether a token exists, then flips `connected = true` and calls
  `announceConnection()`. The auth handshake is sync-layer logic riding on top of "socket opened" —
  it does **not** belong in the transport.
- `electron/sync/syncClient.js:619-630` — `ws.on('message', ...)`: `JSON.parse` in a `try/catch`
  that silently `return`s on failure, then validates the parsed value is a non-null, non-array
  object with a string `.type` before doing anything with it. This exact double-guard is what
  `webSocketClientTransport.js`'s message handler reproduces — framing is a transport concern,
  the guard already lives at the right altitude in the existing code.
- `electron/sync/syncClient.js:828` — `ws.on('error', ...)`.
- `electron/sync/syncClient.js:854-888` — `ws.on('close', ...)`: clears `connected`/`authenticated`,
  settles any pending resolvers with `{ status: 'disconnected' }` (acks/resolvers — sync-layer, stays
  above the seam), and — unless `closedIntentionally` — schedules a reconnect via
  `setTimeout(() => { if (!closedIntentionally) connect() }, RECONNECT_DELAY_MS)` with
  `RECONNECT_DELAY_MS = 1500` (`syncClient.js:317`).
- Send call sites throughout (`syncClient.js:934,940,946,965,1079,1086,...`) are all
  `ws.send(JSON.stringify({ type: ..., ...fields }))` — one uniform shape, which is exactly
  `Transport.send(message)`.
- `electron/sync/syncServer.js` (skimmed): the Host tracks one `ws` per connected client and knows
  which client sent what, i.e. it can attach `meta.peerId` per the contract's `onMessage(handler)`
  note ("`meta` may carry `{ peerId }` when the transport can distinguish peers"). A future S1.3
  server-side transport should wrap the `WebSocketServer`'s per-connection socket map and stamp
  `meta.peerId` from whichever identifier the Host already uses per connection — this file's
  message-handler shape (`{}` meta on the client side, since a lone client has only one peer) is
  written to leave that room without needing a redesign.

## Design decisions

**1. Does reconnect live inside the transport or above it?**

**Recommendation: inside.** `syncClient.js` owns its own reconnect loop today only because `ws`
itself has none — that loop is compensating for a missing transport feature, not expressing
sync-layer policy. The contract's `onStatus` already models a channel that can go
`'connected'` → `'disconnected'` → `'connected'` again; hiding "the socket dropped and
auto-recovered" behind that status stream is the entire value of having a seam. Concretely:
`webSocketClientTransport.js` runs its own `scheduleReconnect()` on `ws.on('close')` (mirroring
`RECONNECT_DELAY_MS`'s value and role), stops scheduling once `stop()` is called (mirrors
`closedIntentionally`), and takes injectable `setTimeoutFn`/`clearTimeoutFn` so a caller (or a
test) can supply a fake timer instead of a real 1.5s wait. When S1.4 eventually migrates
`syncClient.js` onto this transport, its `RECONNECT_DELAY_MS` loop (`syncClient.js:854-888`)
deletes outright rather than growing a second copy alongside the transport's — one reconnect
policy, not two racing ones. `inMemoryTransport` correctly has no reconnect logic because a
loopback pair has nothing to reconnect; that is a property of the carrier, not evidence against
this decision for a real socket.

**2. Where's the transport/sync boundary — do acks stay above?**

**Confirmed: acks and watermarks stay above.** `webSocketClientTransport.js` never inspects
`message.type`; it does not know `submit_op` from `op_applied_ack` from `authenticate`. It also
does **not** attempt to re-deliver a message that was in flight when the socket dropped — see
decision 3 below. The existing sync layer already has its own durable retry path independent of
transport behavior (`pendingWrites.js`, the catch-up watermark `op_applied_ack`, `resolvers`
settled with `{ status: 'disconnected' }` on close) and none of that moves. This transport's only
job is "move this JSON-serializable object to the peer, in order, and tell you when the channel is
up."

**3. Framing / malformed frames.**

Outbound: `JSON.stringify(message)` on `ws.send`, matching every call site in `syncClient.js`.
Inbound: `JSON.parse` in a bare `try/catch`; on parse failure, or on a value that isn't a plain
object with a string `.type`, the frame is silently dropped — never thrown, never surfaced via
`onStatus('error', ...)`. A single bad frame is not loss of the channel; conflating the two would
make `onStatus('error')` noisy and useless as a real signal. This exactly reproduces
`syncClient.js:619-630`'s existing guard rather than inventing new validation rules.

**Documented, deliberate deviation from `inMemoryTransport`:** the in-memory reference buffers
sends made while the peer hasn't started yet and flushes them once it does (`inMemoryTransport.js`'s
`outbox`). A real TCP socket has no such buffer — there is nothing this transport could honestly
hold onto once `send()` is called against a closed connection, and pretending otherwise would
misrepresent the channel exactly the way the ADR's OneDrive field test flagged provider "synced ✓"
claims as untrustworthy. `webSocketClientTransport.send()` therefore rejects immediately
(`Transport ${id} is not started`) whenever the socket isn't `OPEN` — whether that's because
`stop()` was called, or because the socket hasn't finished its initial connect, or because it's
mid-reconnect after a drop. The contract test pins this explicitly
(`webSocketClientTransport.contract.test.js`, "does NOT buffer sends made while disconnected").
This is why store-and-forward durability for the async/offline case is designed to live in the
**folder transport** (S2) and the existing pendingWrites/catchup machinery above the seam, not in
every transport uniformly.

  battery as `transport.contract.test.js`, run against a real `WebSocketClientTransport` talking to

## syncClient.js / syncServer.js / main.js: untouched

No production wiring changed. `electron/sync/syncClient.js` still constructs its own `ws` directly
and runs its own reconnect loop; nothing in the running app imports
`webSocketClientTransport.js`. Rewiring `syncClient.js` onto this transport is **S1.4**, out of
scope here by design, and needs its own Architect design pass (the resolver/ack machinery
currently stashed on the `ws` object in `syncClient.js` has to be re-homed onto
`onMessage`/`onStatus` without changing observable behavior — non-trivial enough to warrant review
on its own, not a rider on S1.2).

## Risk to flag before S1.3/S1.4

- **`noBareSleeps` guard scope.** `electron/sync/noBareSleeps.test.js` scans `electron/sync/*.test.js`
  non-recursively (`fs.readdirSync(__dirname)`), so it does **not** currently see
  `electron/sync/transport/*.test.js` at all. This file's two real-time waits (`unsubscribe stops
  delivery`, tagged `proving-absence`, and `waitFor`'s internal poll, tagged `crossing-interval`) are
  written *as if* the guard applied, in the repo's established idiom, but the guard is not actually
  enforcing that today. Worth a small follow-up ticket to either extend the guard to scan
  subdirectories or explicitly scope it — silent gaps in a guard that exists specifically because a
  bug class recurred twice (T25, T44) are worth closing deliberately rather than by omission.
- **S1.3's `meta.peerId` contract is inferred, not yet built.** This design note states what a
  server-side transport should do (stamp `meta.peerId` per connection, matching how `syncServer.js`
  already tracks per-client sockets) but no server transport exists yet — S1.3 should re-verify this
  against `syncServer.js`'s actual per-connection bookkeeping before committing to the exact shape.
- **Reconnect-loop behavior itself is not covered by this slice's tests.** The contract battery
  intentionally mirrors `transport.contract.test.js`'s scope (connect/disconnect/deliver/order/
  unsubscribe/reject/malformed-frame) and does not add a "socket drops mid-session, transport
  auto-reconnects, onStatus fires disconnected-then-connected-again" test, since the ADR's staged
  S1.2 scope is "same contract, real socket," not full reconnect-under-load coverage. Recommend that
  test be added as part of S1.4's Verifier pass, once real reconnect timing is exercised end-to-end
  against `syncServer.js` rather than a bare `WebSocketServer` stub.
